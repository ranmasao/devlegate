"title": "Add abandoned board and Git-free abandonment ticket workflow"

## Milestone
Introduce an explicit terminal abandonment outcome for unfinished tickets without retaining potentially enormous abandoned implementation branches or granting the summarizing agent Git/control-plane access. This is a new product feature, not an instruction to abandon any existing live ticket.

## Goal
Implement `kanban/abandoned` and a distinct `devlegate.abandonment` request-ticket type. An authorized, reviewed abandonment request names a target ticket, the initial product HEAD and an abandonment reason. Devlegate provides a bounded, verifiable, Git-free read-only evidence view to an agent, obtains a complete semantic abandonment report, moves the target into the terminal abandoned board after review, and retires its exclusive execution resources by reusing the owner-side cleanup machinery. Keep all prior execution JSON and curator review records in control history; no need to retain full unintegrated code or binary blobs merely for historical interest.

## Context
- Current ticket storage accepts `devlegate.ticket` and five boards (`backlog/todo/review/accepted/done`); only `done` satisfies dependencies. `archive/tickets/TASK-134.md` is a historical one-off outside the DAG, not a supported board.
- Existing `devlegate drop` applies to one narrow blocked lifecycle execution. Existing `cleanup_workspaces` / `_retire_execution_refs` already implement guarded worktree/local/remote retirement, but their current admission depends on a durably `done` ticket and product integration. Neither contract is a general abandonment.
- Multiple executions of one ticket may have different `code_base_head`, checkpoints, reviews, rework/deferred generations, and pinned `refs/devlegate/**` code evidence. A single final branch diff does not describe the work or failed approaches. TASK-150 introduces generation-specific local resource proof; upstream ref continuity cannot be inferred from matching ref name and SHA.
- The existing worker `devlegate_report` egress and independent reviewer are suitable semantic/report boundaries. Ordinary implementation workers are instructed not to operate Git, but the abandonment analysis worker must actually receive only a controlled, Git-free view, not an accessible checkout/credentials hidden behind prompt instructions.
- Do not implement the old TASK-129–132 universal reset protocol, change or run TASK-133, automatically abandon TASK-073/129–132, or introduce historical state migrations. First implementation execution will be reviewed before any real operator-resource retirement.

## Required behavior

### A. Board, schema and scheduling
1. Add terminal `kanban/abandoned` as a first-class configured workflow path, fingerprinted, validated, counted and represented in status/plan/docs/templates as appropriate. Preserve five existing states and existing ticket behavior. `abandoned` is known to dependency validation but never satisfies a dependency or becomes runnable. Dependants on abandoned tickets remain valid, explicitly blocked with that reason, not spuriously `done` or a missing-dependency failure.
2. Add `devlegate.abandonment` as a distinct *request ticket* type, not a new implementation worker claim. Its restricted NanoYAML metadata must identify exactly one target ticket ID and an explicit full initial product HEAD (`target`, `start_head`); its body must contain a concrete `Abandonment reason` and report requirements. Keep ordinary `devlegate.ticket` metadata validation strict. The request itself follows its own normal review/acceptance flow and is marked `done` only on successful finalization; the *target* becomes `abandoned`. Target identity and reason must be bound to the admitted control ticket blob; an amendment must not silently retarget work.
3. Treat an admitted abandonment request as an exclusive target disposition: prevent new target worker admission while it is being processed, and prioritize the request over an otherwise runnable target. Reject same-target concurrent/conflicting requests, self-targeting, missing/already terminal targets, and any live worker, pending integration/reconciliation/recovery or other uncertain target ownership. Do not terminate an active worker or declare unrelated resources disposable. Fail closed with an actionable refusal.

### B. Deterministic owner-side evidence extraction
4. Under the existing service owner/Git capability, build a read-only evidence manifest from the exact target specification, ordered control history, immutable ExecutionReports, bound curator reviews, the requested `start_head`, every independently verified execution `code_base_head` and checkpoint, and the current owned resource observation. Verify paths, SHAs, lineage and generation claims. Order by proven control history, never execution-ID lexical order. Preserve unavailable, conflicting or unproven material as explicit gaps; never fabricate a diff or silently fall back to an older checkpoint.
5. Supply both (i) per-execution base-to-checkpoint deltas with review decisions and (ii) a clearly labelled latest/final state comparison *only where the relevant ancestry is proven*. Avoid treating one diff from the original HEAD to a rebased/advanced final HEAD as the cumulative contribution of the target ticket. Include file status, path, size, content hash and bounded text excerpts; identify renames, deletions, submodules, binaries and missing objects.
6. Enforce independently testable conservative defaults for inline material: at most 256 KiB of any individual file/diff excerpt and 4 MiB aggregate inline diff/text for one analysis bundle. Exceeding a limit MUST create a truncation/index entry, not an invisible omission, a failing huge prompt, or a copy of entire binary content into control history.
7. Provide on-demand, read-only, **bounded** access to omitted artifacts (including binary data and large diffs): a stable manifest-scoped artifact ID, exact source identity/content digest, byte offset and length, bounded per-call read (e.g. 256 KiB), and text or explicitly encoded bytes. Support paging through a large file or diff without Git commands/refs/path guessing by the agent. Guard against path traversal, arbitrary filesystem reads, resource substitution after manifest creation, changed/absent underlying objects, symlinks, and unbounded memory/prompt accumulation. Do not eagerly mirror every giant object into a persistent bundle. Prefer a minimal owner-mediated artifact reader or a precisely scoped read-only materialization with equivalent bounds over a generic new API/server.
8. The analysis agent runs in an isolated, Git-free evidence workspace, without project/worktree `.git`, Git credentials, privileged control IPC or direct mutable repository access. It may request only authorized manifest objects through the bounded read mechanism and cannot modify source/control resources. Reuse existing worker execution, reporting and process-isolation infrastructure where possible; if the required isolation cannot be proved, report the limitation and do not claim the feature complete.

### C. Review, finalization and retirement
9. Have the analysis agent produce a substantive final abandonment report through a bounded existing or narrowly extended `devlegate_report` output. At minimum: explicit reason, outcome of each execution/review, meaningful changes and research, integrated versus discarded work, unfinished work, known gaps, useful future conclusions, and the exact manifest/checkpoint identities used. The semantic claim is untrusted; Reviewer validates the report. Do not publish it as an authoritative terminal result from an unreviewed worker claim.
10. On exact reviewer acceptance, under one serialized, replayable control transition, publish the reviewed report *after* existing target reports/reviews (e.g. `abandonments/<target>/<request-execution>.md`), move the unchanged target ticket to `kanban/abandoned`, and complete the request ticket, without merging its analysis artifacts into the product branch. No false `done` of the target, no direct worker Git mutations, and no orphaned duplicate terminal report on replay.
11. The canonical published `abandoned` state authorizes retirement of **resources belonging to that target**, without additional proof that the code is unneeded and without product-ancestry/integration requirements. Reuse the existing owner-serialized worktree/branch/ref retirement operations, expected-old local CAS, remote lease and replay guards; provide an abandonment-specific authorization check instead of weakening the `done` proof. Retire the registered owned worktree (including dirty/untracked files only after exact ownership and final report publication), local and upstream `devlegate/work/<target>` refs and **exclusive** code-pinning evidence refs that would otherwise keep large abandoned Git objects reachable. Never delete shared/product/control refs, immutable execution JSON, curator reviews, the abandonment report, or foreign/unproven resources. Remote matching SHA is not proof of uninterrupted identity; do not claim otherwise.
12. Abandonment is terminal even if post-transition cleanup is temporarily `pending`/`blocked`. Persist precise cleanup intent/status, reobserve ownership at every destructive boundary, and resume safe partial retirement across process loss. Unknown remote state, competing owner, changed ref, active lease, dirty foreign checkout, or ambiguous generation stops the destructive action and surfaces an operator-actionable reason, not a fabricated successful cleanup. Avoid long polling or repeated costly checks for other non-done tickets.

## Acceptance criteria
- `devlegate.abandonment` is a schedulable typed request with strict target/start-head/reason validation; standard tickets and their existing review/integration semantics remain unchanged.
- `abandoned` is a visible sixth terminal Kanban state with valid dependency graph semantics; a dependent ticket is blocked by `abandoned` rather than missing its dependency.
- A disposable real-Git fixture with at least two reviewed/reworked execution generations on different bases produces a deterministic chronological, attributable manifest; a Git-free analysis worker can obtain bounded excerpts *and* subsequently read omitted full content in chunks (including an oversized binary) without any direct Git access.
- Exactly one independently reviewed abandonment report is published after target reports/reviews and before destructive cleanup; the target becomes `abandoned`, the request becomes `done`, and no unintegrated product code is merged.
- Only provably target-owned resources are retired using shared cleanup primitives; local/remote refs and exclusive code pins are absent afterward, including on restart/replay. A blocked cleanup does not reverse the terminal board state or destroy historical text evidence.
- Focused real-Git, owner/IPC and reviewer tests pass, plus configured CI/Ruff. Document operator workflow, limits, remote-identity caveat, report placement and recovery behavior.

## Required regressions
1. Existing five-board fixtures and ordinary ticket metadata load unchanged; malformed abandonment target/start HEAD/reason or metadata extra fields fail validation. Duplicate/cyclic dependencies still fail.
2. A `todo` ticket depending on an `abandoned` ticket stays blocked and the control graph remains valid; pending abandonment of a runnable target cannot race a new worker admission.
3. Two executions with distinct base HEADs and rework reviews produce separate accurate deltas, not a misleading original-to-final diff. Missing checkpoint/altered review/unreachable blob causes an explicit bundle gap or safe block, never an invented history.
4. File just below and above 256 KiB, aggregate diff just below and above 4 MiB, renamed file, huge binary, non-UTF-8 data, and large text diff retain index entries; selected byte ranges are digest-verified and readable without Git by the agent. Invalid offsets, unauthorized artifact IDs, stale objects, symlink/path traversal and excessive read sizes are denied.
5. Unreviewed, rejected or failed summary cannot abandon anything or retire refs; accepted review yields one final report and exact board transition, including duplicate delivery and crash/restart during control publication.
6. Cleanup disposes an authorized dirty *owned* abandoned worktree, exact local and remote ticket branch and exclusive code-pinning refs; preserves product/control history and immutable text reports. An ambiguous/foreign worktree, changed branch SHA, failed remote observation, live worker, pending reconciliation, or conflicting generation blocks without partial unauthorized deletion. Interrupted partial deletion can be retried safely.
7. No TASK-073, TASK-126, TASK-129–133, TASK-134 archival evidence or existing operator resources are altered by tests or first implementation run.

## Boundaries
Prefer an incremental, reviewable implementation reusing existing ticket, service-owner, worker egress, review provenance, Git and cleanup boundaries. Keep stdlib-only runtime; avoid broad VCS abstraction, historical migrations, generic reset engines or changes to TASK-133. Never perform destructive abandonment against the actual hosted project during this implementation ticket. Do not split off unrelated follow-up tickets or claim completion without the full contract; the curator will inspect the first execution/report before deciding any hardening or scope refinement.
