## Problem

The owner can reconcile a worker checkpoint onto a newer product base via `devlegate reconcile update-base` only when the *active* execution previously persisted `reconciliation.status=pending`. After an infrastructure/transport failure has been reported and the ticket deliberately deferred `todo → backlog → todo`, the owner is `idle`, so no reconciliation may be admitted. Instead, `_latest_reviewed_rework_report()` sees a newer failed execution followed by an older genuinely reviewed generation and unconditionally refuses new work.

The concrete retained example is TASK-134: reviewed execution `0c944f7c8bb741a4a367c95c4cfc10d0` has immutable curator feedback; later transport-failed execution `3cb61e2d366042aeab97caf3f4702ece` has checkpoint `7c8274a837bd5579b3ac607bd570ff8d14e5016b` and 18 linear worker commits since its admitted base `5b81966afab8eac2d021332c22a04a34361736ef`. Product `release/0.5.7` advanced independently to `d0572c6f7704b138ed9e7cabb33ba4c025001a89`. The ticket's immutable `review → todo → failed → backlog → todo` disposition is now recognized by TASK-138, but requeued work still cannot run; `devlegate plan` says `run-worker` while owner-side admission is blocked.

An outdated worker base is normal for future concurrent executions. It is not by itself evidence of corrupted resources. The missing operation is the admission of a *retained, historical* failed checkpoint to the existing reconciliation/repair workflow, not another Git rebase implementation.

## Goal

Extend the current owner-controlled `reconcile` workflow to repair a deferred failed execution against the current product base when its checkpoint and historical review binding are sufficiently proven, or when an operator explicitly authorizes a bounded historical ownership assumption. Retain original worker delta, original immutable curator feedback, all prior reports and evidence. A transport-failed generation remains failed and must never be relabeled as reviewed. Do not create a new reset or generic force-retry subsystem.

## Implementation contract

1. **Admission and observation.** Provide an explicit operator-initiated repair mode within the existing reconciliation CLI/IPC/owner lifecycle (or a carefully justified extension of `reconcile update-base`). Identify the exact ticket, failed execution report/id and checkpoint, prior reviewed execution and immutable feedback, canonical ticket blob and first-parent transitions, current clean product HEAD, local/remote execution refs, registered worktree identity/path/HEAD/cleanliness/submodules, worker absence, and any pending intents. Never treat names, paths, or matching SHA alone as proof of uninterrupted ownership. Do not admit from ordinary `run-worker` merely because an old failed report exists.
2. **Historical boundary.** Distinguish independently proven generation continuity from unavailable historical ownership evidence. If continuation requires operator acknowledgment of that missing historical proof, make it explicit, single-generation, identity-bound, observable and revocable on drift. Do not fabricate a preexisting BOUND record, relax TASK-134's prospective generation-ownership contract, or silently reuse `retry --force`. Uncertain or foreign resources must block without side effects.
3. **Reuse reconciliation.** Admit a durable, owner-serialized reconciliation intent under existing WAL/CAS conventions, pin the entire displaced checkpoint/delta and original review evidence before any mutation, then reuse or narrowly factor existing `reconciliation_transactions` update-base machinery (including actual `git rebase --onto`, linear ancestry proof, clean-workspace checks, local expected-old ref update, remote `--force-with-lease` when explicitly authorized, and restart replay). A conflict must abort safely with old lineage retained; failures/restarts must not duplicate workers or lose refs/submodule state. Avoid a parallel implementation of ref rewrites.
4. **Successful result.** Repaired worker code is based on the current product generation and preserves the cumulative failed checkpoint changes (or proves an intentional no-op/already-integrated case). Schedule/prepare a *new* execution identity with the originally published curator feedback; do not credit the old failed execution with an invented review. Make owner admission observe the recorded repair disposition rather than hit the existing unconditional failed-after-reviewed blocker. Preserve the historical reports, checkpoint refs, control history and canonical ticket bytes.
5. **Regressions.** Add isolated real-Git end-to-end coverage of review publication → transport failure with nonempty delta → deferral/requeue → advanced product base → owner repair → restart → new worker receiving original review and preserved delta. Also test dirty/missing/foreign/locked worktree, uncertain/recreated identity, changed local or remote ref, stale authorization, control/product drift, rebase conflict, retry of partially completed operation, concurrent commands and crash boundaries. Assert old evidence untouched in all outcomes.
6. **Documentation and validation.** Document command usage, exact effect of operator authorization, expected ownership limitations and restart/conflict handling. Run focused and full configured CI plus Ruff on the final checkpoint. No migrations, compatibility scaffolding, TASK-134-specific production conditional, manual rewriting of old review/report files or alteration of actual historical TASK-134 resources in tests.

## Boundaries

This task extends *repair/reconciliation*, not reset, eviction, or autonomous force-retry. Keep `TASK-129 → TASK-132` reset work independent. TASK-134's original prospective BOUND-proof requirement remains unchanged; no dependency on unfinished TASK-134 may be introduced. The next runnable ticket can be this repair enhancement while TASK-134 remains safely deferred. After accepting/integrating this task, the operator may explicitly return TASK-134 to `todo` and invoke the documented repair operation with exact observed identities; do not automatically mutate TASK-134's retained worktree during implementation.
