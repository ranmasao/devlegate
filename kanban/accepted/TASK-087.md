## Context
The generated `skills/architect/SKILL.md` and `skills/reviewer/SKILL.md` act as role contracts for curator decisions. The packaged worker prompt is assembled separately from the core contract, FRESH/REWORK/RESUME directives, the canonical ticket and the applicable current review. The project now has review artifacts, multi-generation rework, exact-checkpoint CI, provenance and remote evidence protection, installed-runtime dogfooding, and a strong objective to minimize HitL. The current documents may be stale, excessively procedural, missing critical obligations or poorly structured for LLM use.

TASK-094 already repaired deterministic injection of current review feedback and role-template upgrade/migration. This task must inspect the resulting deployed contract and reuse that infrastructure rather than reopen feedback provenance or silently override project-customized materializations.

A controlled real-world observation from TASK-108 (2026-10-27/28) motivates this audit: GPT-6.1 Terra produced nine short, useful, separately checkpointed executions of the same broad ticket, all claiming `incomplete`, often with actionable `todowrite` items still pending. After a model switch, GPT-5.6 Terra produced one `incomplete` and two `completed` executions; its first `completed` was rejected because the claimed complete audit contradicted a stale document, and the next passed independent review. The observations are confounded by different starting code states, task breadth, review feedback, model behavior, and agent environment; do not assert a model defect or infer hidden reasoning. Treat them as concrete prompt/contract test cases.

## Goal
Independently assess whether the architect, reviewer **and worker** prompts express the correct role authorities, workflow and acceptance standards; whether `SKILL.md` and packaged prompt texts are the right forms; how execution termination should be distinguished from intermediate work-unit completion and ticket acceptance; and how these contracts can be maintained and tested without expanding Devlegate's deterministic control-plane authority unnecessarily.

## Required study
1. Read **actual generation and delivery sources**: packaged `core_contract.txt` and FRESH/REWORK/RESUME texts, `src/devlegate/worker_prompt.py`, relevant supervisor/egress/report handling, architect/reviewer source templates and materialized skills, `.devlegate/project.md`, current Kanban and independent review examples, lifecycle implementation and test/verification policy. Identify what the *running* service uses versus repository sources, project-owned overrides, managed generated assets and runtime upgrades. Note stale generated references against configured behavior; verify rather than assume.
2. Audit role separation and permitted operations: architect specifies/prioritizes and authors canonical tickets; worker implements and makes bounded, honest outcome claims but does not move workflow state; reviewer independently evaluates the exact checkpoint, requirements and evidence and moves `review -> todo` or `accepted`; engine owns integration/`done`. Ensure no guidance invites unsafe direct Git mutations, bypasses ownership, or equates worker `completed` with acceptance.
3. **Worker termination contract:** reconstruct the currently visible meaning and use of `completed`, `incomplete` and `blocked`, together with FRESH/REWORK/RESUME and any agent/tool finish constraints. Distinguish (a) coherent subtask finished, (b) all ticket requirements satisfied, (c) inability to continue safely/productively during this invocation, and (d) external information/action needed. Propose minimal model-neutral text that discourages voluntary handoff merely because one safe patch or focused test finished, without mandating unsafe continuation, wall-clock busywork, or a forced `completed`. State an explicit truthful reason for `incomplete` when useful work remains. Preserve shutdown, checkpointing and the current worker report protocol unless a separately justified implementation follow-up is required.
4. **Ticket scope and acceptance:** examine whether existing required behavior, regressions and acceptance criteria are sufficiently clear and appropriately scoped. Consider splitting oversized tickets into independently reviewable dependent tickets. Completion remains a semantic assessment against the full ticket; local `todowrite` completion is insufficient. Formal DoD schema, criterion identifiers and tracking are deferred.
5. **Deterministic versus semantic verification:** enumerate what Devlegate can enforce mechanically (ticket identity, exact checkpoint/CI provenance, report structure, workflow transitions) versus what only a semantic reviewer can judge (adequacy, coverage, complete inventory, coherence of tests and documentation). Assess whether any structured machine reporting is *necessary* rather than assuming new ticket protocol fields or automatic semantic acceptance.
6. Test the documents against **concrete decision scenarios**: TASK-108-style worker `incomplete` despite pending actionable subtasks; a valid short unit with continued execution possible; real blocker; imminent shutdown; zero-delta retry; worker `completed` with stale contradictory audit; red/pending CI; absent report artifact; consecutive rework; safe workflow moves; installed versus running runtime; autonomous diagnosis and escalation. Distinguish evidence visible in OpenCode/Devlegate traces from hypotheses about model intent. Include a concise decision matrix showing expected worker claim and reviewer disposition.
7. Assess information architecture: short role entrypoints versus normative policies/references/checklists, structured machine-checkable contracts where warranted, prompts/examples, duplication, drift prevention, versioning, generation ownership and token/context overhead. Compare viable formats instead of assuming more `SKILL.md` prose is always better. Include a minimal, testable prompt-only change candidate and a separate architect ticket-scope guidance candidate; do not conflate their effects in evaluation.
8. Propose a coherent revised prompt/skill/ticket structure and migration/validation plan with testable behavior scenarios, source-of-truth and exact project-template regeneration pathways, and small prioritized follow-ups. If later implementation is approved, provide a controlled evaluation plan comparing otherwise-similar executions on real tickets, tracking honest outcomes, reviewer findings, tool calls, tokens/cache usage and work re-read overhead. Avoid treating the historical TASK-108 sequence as an independent A/B trial.

## Implementation and deployment directive — 2026-10-28

The curator requests this ticket implemented during release 0.5.7, not merely investigated. Preserve the existing implicit completion criteria (`Required behavior`, `Required regressions`, `Acceptance criteria`); **do not** introduce a strict Definition of Done schema or per-criterion protocol.

1. Update the packaged core worker contract, and only the FRESH/REWORK/RESUME directives that actually require wording changes. Specify that an intermediate task, passing focused tests, or a tidy checkpoint **does not itself justify** calling `devlegate_report(incomplete)`; while productive and safe work remains, continue toward the whole canonical assignment. `completed` requires honest assessment of the entire ticket, not merely local `todowrite`. `incomplete` remains valid when this invocation must end while actionable work remains, with concrete remaining actions and a truthful stop reason within the existing report fields; `blocked` is for missing external decisions/actions. Do not fabricate reasons or turn all partial progress into a block. Preserve worker Git/workflow prohibitions and feedback fencing.
2. Clarify architect source template guidance on writing bounded tickets and clear existing acceptance criteria, and reviewer source template guidance on evaluating the complete canonical assignment and cumulative proof independently of the worker outcome. Maintain TASK-094 separate review artifact semantics, both template source locations and controlled generated/materialized artifact handling. Avoid duplicated verbose rules, and do not attempt to implement autonomous reviewers.
3. Add focused unit/integration regressions for prompt byte composition, role template regeneration, FRESH/REWORK/RESUME unchanged feedback provenance, and explicit scenario-based policy assertions: actionable pending work, valid external blocker, interrupted execution, and false `completed`. Keep the policy semantic; don't implement keyword-based outcome policing in Devlegate. Verify packaged assets and standalone artifact pickup, then run exact-checkpoint CI.
4. Prepare the **two local project update** procedure for Devlegate itself and `rslab2`: require installing the newly integrated 0.5.7 build on the host that runs each service, restarting the service so its Python packaged prompt is reloaded, and invoking `devlegate upgrade-templates --check` / `devlegate upgrade-templates` in each project when appropriate. Detect and report customized template conflicts rather than overwrite them. Explain how to compare persisted worker prompt artifact hashes/newly admitted executions; do not claim existing running executions change retroactively.
5. The worker cannot access arbitrary operator machines. Do not claim either machine was updated unless the operator executes and verifies the deployment commands. Do not mutate the separate `rslab2` source tree or private runtime state from this ticket. If implementation cannot safely complete, report truthful `incomplete` with actionable remaining work.

**Acceptance:** packaged core prompt and both maintained role templates express coherent completion/termination semantics; focused tests and exact-checkpoint CI pass; documented commands install and activate the change for two existing projects without bypassing ownership; no strict DoD fields or unapproved control-plane modifications.
