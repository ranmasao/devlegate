## Purpose and scheduling
**Next iteration only.** Keep this ticket in `backlog` until an explicit curator scheduling decision; do not promote it to `todo` merely because dependencies are done. Implement Git-native specification amendments by ordinary commits/pushes to `devlegate/control`, without a new CLI amendment operation or any change to existing ticket YAML front matter / Markdown format. Preserve the existing strict workflow and review provenance guarantees, with a new explicitly distinguishable amendment generation.

## Required contract
1. A ticket specification is identified by its exact Git blob and control commit provenance. Existing workflow moves without specification changes remain strict blob-preserving transitions. A normal Git commit that changes a ticket's content at its stable path/ID constitutes a candidate amendment only under an explicitly supported ticket state and safe execution boundary. A commit author/name is not proof of operator authorization: rely on control-branch write governance and supported owner/admission checks.
2. Permit amendments of `backlog` tickets and `todo` tickets that are not admitted/bound to an execution. Preserve scheduler re-evaluation of `depends_on`, ticket schema and DAG constraints. An amendment cannot silently mutate a bound worker's specification, execution prompt, product/control admission or recovery authority. Define fail-closed behavior for active/pending execution and distinguish concurrent control changes.
3. Treat `review`, `accepted` and `done` as protected states: do not quietly amend a reviewed result, accepted integration or completed history. Determine a narrow explicit Git-native route for amendment after valid review deferral (e.g. immutable `review -> backlog`, separately committed amendment at backlog, later `backlog -> todo`). Do not weaken the existing `review -> todo` equality check for ordinary rework.
4. An amended deferred ticket creates a **fresh specification/execution generation**, not an old-generation REWORK or RESUME. Adjust `review_provenance.resolve_rework_review` and runtime admission to recognize an unambiguous intervening amendment history when supported; previous review feedback and execution reports remain immutable historical evidence, not falsely attributed to the new generation. Establish whether and how old worktree/local/upstream refs must be explicitly retired under the operator reset protocol (TASK-129–132); never silently delete non-done resources.
5. Verify Git history/identity rigorously: exact blob and path transitions, monotonic authorized control history, unchanged ticket ID, no deletion/recreation masquerade, ambiguous/multi-step/cross-state changes, race against active admission, rewritten remote refs, missing objects and failed Git observations. Fail closed with actionable diagnostics; do not treat errors as absence.
6. Document operator Git workflow with concrete examples (edit, commit, push), permitted states, rejection/retry/recovery rules, and relationship to explicit resource reset. No dedicated amendment metadata/trailers required in ticket itself; no generic VCS abstraction, migration path or compatibility scaffolding.

## Acceptance
Focused unit and real-Git integration coverage for: backlog amendment; unbound todo amendment and dependency rescheduling; immutable review deferral then amendment then fresh todo execution; unchanged-spec rework retains original review binding; active/recovery/integration refusal; accepted/done history protection; malformed transitions and SHA races; fresh generation and old evidence preservation. Retain WAL/CAS, owner serialization, historical audit integrity and full configured CI. Provide a concise provenance-state matrix and exact operator examples. Do not auto-accept prior work or change TASK-073's human approval gate.
