## Why this follow-up exists

TASK-066 was accepted and integrated with green CI and genuine bug fixes, but its original DRY acceptance was **not fully audited or fulfilled**. It extracted a correct shared byte-positioned `_LogCursor`, but retained parallel orchestration of ticket/execution selection, active-state polling and directory traversal. Do not reopen or undo the integrated TASK-066 work. This task closes only the remaining demonstrable duplication and call-path inconsistency.

## Current duplication / evidence (release/0.5.7 at 507da8f926f9)

- `src/devlegate/log_reader.py`: `ticket_log()` (~286) and `follow_ticket()` (~311) separately enumerate reports, resolve active execution, build history output and choose whether to use `_read_file()` or `_follow_execution()`. They share helpers but **do not share one coherent execution-selection model**. This can cause observable initial-output differences when history + current execution overlap.
- `_current_execution_id()` (~47), `_active_ticket_execution()` (~259), and `_execution_active()` (~437) separately read `SQLiteRuntimeStore.load()` and repeat phase/identity checks.
- `_execution_candidates()` (~112) and the unscoped `_execution_report()` (~449) each enumerate the `executions/<ticket>/` directories with partly duplicated validation rules. For `logs execution -f`, `_execution_terminal()` can repeat that unscoped directory walk roughly every 100 ms when `ticket_id` is not supplied; identify execution and owning ticket only once where possible, then use targeted exact report checks.
- `execution_log()` (~215), CLI follow resolution at `src/devlegate/cli.py` (~2281), and `follow_execution()` (~568) do not share a single resolved execution-target abstraction. Keep the same public CLI and minimal number of calls; avoid redundant work.
- `follow_file()` (~421) is not currently invoked by CLI. Verify all call sites and either remove the unused entry point with appropriate test updates or justify why it is intentionally retained; avoid a third independent file-follow engine.
- `journalctl` is a distinct backend. Shared command construction already exists; do not force journal subprocess streaming into file cursor semantics.

## Required work

1. Inventory before/after actual reuse, including each of the call paths above; distinguish *necessary* differences (snapshot vs follow, ticket vs execution lifetime) from duplicated resolution, validation and common initial-output logic.
2. Consolidate actual duplicated **ticket/execution selection and active-state observation** into a small set of cohesive helpers. Normal log read is the initial finite portion of the *same* conceptual stream; `--follow` continues it, not a separately defined history algorithm. It is acceptable to retain separate public entry points and file/journal process loops if they delegate shared semantic decisions.
3. Avoid rescanning the whole `executions/` tree on each follow poll when the execution's ticket binding can be established and preserved. Share safe candidate enumeration/validation logic, keep requested corrupt evidence fail-closed, and ensure unrelated malformed reports cannot block a bound ticket/execution.
4. Preserve the integrated `_LogCursor` and precisely once handoff; avoid extra file opens, hidden polling amplification, repeated report parsing or new instrumentation frameworks. Handle active/terminal SQLite transition, retries, missing expected logs, accepted-before-done and multiple executions without regressions.
5. Add narrowly focused **log-data parity tests** proving identical initial raw log lines for `logs ticket T` vs `logs ticket T -f`, and `logs execution E` vs `logs execution E -f`, with the same `--tail N` or `--all` and stable snapshot. Exclude presentation markers from raw-data comparisons. Include multiple historical reports plus active execution, a tail crossing execution boundaries, `--tail 0`, `--all`, report-before-SQLite handoff and subsequent append. Avoid sleeping/flaky integration timing; retain malformed-unrelated/requested report tests.
6. Keep `cli.py` thin, no generic LogSource/streaming framework, no new dependencies, no cosmetic forwarding layers or Protocol expansion. Do not change report schema or storage paths. CLI syntax changes are restricted to the explicitly specified options below.
7. Implement the agreed CLI option contract for `logs ticket`, `logs execution` and `logs service`: `-t N` / `--tail N` (nonnegative count of source log lines), `--all` (full available history) and `-f` / `--follow`. `--all` and explicit `-t` / `--tail` are **mutually exclusive**, rejected by argument parsing even when the explicit tail is 100. With neither specified, default to `--tail 100`. `--follow` is independent: `--all -f` prints all existing history then follows new lines; `--tail 0 -f` starts at the current EOF and prints only subsequent lines. Retire the experimental `--lines` option rather than retaining a compatibility alias. For `logs service`, map bounded/full history to the appropriate `journalctl` behavior without conflating its backend with execution file cursors.
8. Define `--tail N` for `logs ticket T` over the **one logical concatenation of all execution logs in chronological execution order**, not N lines per execution and not just the newest execution. E.g. if older E1 has 200 lines and newer E2 has 80, `--tail 100` prints the final 20 E1 lines followed by all 80 E2 lines. `--all` prints every available line across all executions. Preserve exactly-once continuation across execution boundaries with `-f`, including new executions created after following begins. Synthetic headers and status markers are excluded from source-line counts. Avoid eager full-history materialization for bounded tail reads where possible, without introducing N+1 polling or redundant file scans.
9. Expose `--suppress-markers` on `logs ticket` and `logs execution`, with or without `--follow`. By default show human-readable **presentation markers in stdout**, including execution boundary headers and explicit final status markers; they are *not* error diagnostics. Suppression removes **all** Devlegate-generated markers (including execution separators), leaving only raw log records on stdout; real failures remain stderr diagnostics with a nonzero exit status. Do not alter original log content or conflate synthetic markers with data.
10. On successful finite reads without `-f`, print a visually obvious final marker even if there are zero selected raw lines: for an execution, report the authoritative execution conclusion (`completed`, `incomplete`, `failed`, etc.) when evidence exists, or indicate active/nonterminal state; for a ticket, distinguish `done` (integrated), `accepted` (awaiting integration), `review` (awaiting review), `todo`/rework, backlog, and any current execution with its known result. State that a finite **snapshot is complete** when the underlying entity is not terminal; reaching EOF alone never proves execution/ticket completion. Successful read and successful execution are different claims. After `-f` ends *naturally*, print a corresponding terminal marker: execution follow waits for durable execution completion evidence and log EOF; ticket follow waits for `done`/integration and log EOF. Do not claim terminal success on Ctrl+C, read/validation failure, absent expected evidence, or premature exit. `--suppress-markers` also suppresses terminal markers. `logs service` has no execution/ticket lifecycle to infer; do not fabricate one.
11. Keep output ordered and deterministic, including logs whose final record lacks a newline: markers must be visibly separated but must not silently change the raw log bytes. Preserve raw-data parity between finite and follow modes, preserve `stdout` for normal data and presentation markers, and use `stderr` for actual command failures. Do not add extra state reads, new persistence, hidden background processes, or a new logging framework merely for marker presentation.

## Acceptance for curator

- Provide a compact map of former duplicated blocks to actual shared implementations; specify distinct logic intentionally retained and why. **An `_LogCursor` shared beneath otherwise parallel history-selection algorithms does not alone satisfy this task.**
- Quantify whole-directory enumeration and SQLite/report observation frequency for representative snapshot/follow flows, before/after. No new hidden polling, file opens or semantic side effects.
- Demonstrate identical selected raw log lines on stdout, excluding synthetic markers, and no duplicate/missing source lines across snapshot/follow and execution transitions. The global ticket `--tail N` limit counts source lines across executions, while `--all` returns the complete available history. Marker presentation must not change the raw data.
- The parser enforces `--all` XOR explicit `--tail N` (including `-t N`) on all three log sources, with default `--tail 100` and independent `-f`; `--tail 0 -f` follows only new lines, and `--all -f` follows after full history. The obsolete `--lines` option is absent.
- Finite ticket/execution reads end with explicit, **stdout** lifecycle-aware snapshot markers; natural terminal follow completion also produces status markers. For ticket, `done` specifically means integrated, not merely the latest execution completed. Markers do not falsely report terminal success for active entities or errors. `--suppress-markers` removes final and intermediate synthetic markers and leaves original log records unchanged, while actual errors use stderr and a nonzero exit status.
- Full exact-checkpoint pytest and Ruff green, plus focused regression evidence. No closure based solely on CI without DRY inspection.
