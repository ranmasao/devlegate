## Context
The generated `skills/architect/SKILL.md` and `skills/reviewer/SKILL.md` act as role contracts for curator decisions. The packaged worker prompt is assembled separately from the core contract, FRESH/REWORK/RESUME directives, the canonical ticket and the applicable current review. The project now has review artifacts, multi-generation rework, exact-checkpoint CI, provenance and remote evidence protection, installed-runtime dogfooding, and a strong objective to minimize HitL. The current documents may be stale, excessively procedural, missing critical obligations or poorly structured for LLM use.

TASK-094 already repaired deterministic injection of current review feedback and role-template upgrade/migration. This task must inspect the resulting deployed contract and reuse that infrastructure rather than reopen feedback provenance or silently override project-customized materializations.

A controlled real-world observation from TASK-108 (2026-10-27/28) motivates this audit: GPT-6.1 Terra produced nine short, useful, separately checkpointed executions of the same broad ticket, all claiming `incomplete`, often with actionable `todowrite` items still pending. After a model switch, GPT-5.6 Terra produced one `incomplete` and two `completed` executions; its first `completed` was rejected because the claimed complete audit contradicted a stale document, and the next passed independent review. The observations are confounded by different starting code states, task breadth, review feedback, model behavior, and agent environment; do not assert a model defect or infer hidden reasoning. Treat them as concrete prompt/contract test cases.

## Goal
Independently assess whether the architect, reviewer **and worker** prompts express the correct role authorities, workflow and acceptance standards; whether `SKILL.md` and packaged prompt texts are the right forms; how execution termination should be distinguished from intermediate work-unit completion and ticket acceptance; how a ticket Definition of Done (DoD) could improve decomposition and evidence; and how these contracts can be maintained and tested without expanding Devlegate's deterministic control-plane authority unnecessarily.

## Required study
1. Read **actual generation and delivery sources**: packaged `core_contract.txt` and FRESH/REWORK/RESUME texts, `src/devlegate/worker_prompt.py`, relevant supervisor/egress/report handling, architect/reviewer source templates and materialized skills, `.devlegate/project.md`, current Kanban and independent review examples, lifecycle implementation and test/verification policy. Identify what the *running* service uses versus repository sources, project-owned overrides, managed generated assets and runtime upgrades. Note stale generated references against configured behavior; verify rather than assume.
2. Audit role separation and permitted operations: architect specifies/prioritizes and authors canonical tickets; worker implements and makes bounded, honest outcome claims but does not move workflow state; reviewer independently evaluates the exact checkpoint, requirements and evidence and moves `review -> todo` or `accepted`; engine owns integration/`done`. Ensure no guidance invites unsafe direct Git mutations, bypasses ownership, or equates worker `completed` with acceptance.
3. **Worker termination contract:** reconstruct the currently visible meaning and use of `completed`, `incomplete` and `blocked`, together with FRESH/REWORK/RESUME and any agent/tool finish constraints. Distinguish (a) coherent subtask finished, (b) all ticket requirements satisfied, (c) inability to continue safely/productively during this invocation, and (d) external information/action needed. Propose minimal model-neutral text that discourages voluntary handoff merely because one safe patch or focused test finished, without mandating unsafe continuation, wall-clock busywork, or a forced `completed`. State an explicit truthful reason for `incomplete` when useful work remains. Preserve shutdown, checkpointing and the current worker report protocol unless a separately justified implementation follow-up is required.
4. **Ticket decomposition / DoD:** evaluate introducing a clear Markdown Definition of Done section with stable criterion labels and observable, reviewer-verifiable outcomes; distinguish normative required behavior, implementation work plan, regressions, evidence, and acceptance criteria. Prefer additive Markdown structure compatible with existing NanoYAML frontmatter and current parser; do not invent unsupported metadata. Architect should write verifiable properties rather than dictate every implementation step, decide when a broad ticket should be split into dependent tickets, and permit discovery of additional safety requirements. Ensure a worker cannot satisfy DoD simply by marking local `todowrite` entries completed. Reviewer evaluates cumulative checkpoint evidence across rework generations and revisits prior proof when invalidated by new changes.
5. **Deterministic versus semantic verification:** enumerate what Devlegate can enforce mechanically (ticket identity, stable DoD labels if formally adopted, exact checkpoint/CI provenance, report structure, workflow transitions) versus what only a semantic reviewer can judge (adequacy, coverage, complete inventory, coherence of tests and documentation). Assess whether any structured machine reporting is *necessary* rather than assuming per-DoD control-plane states, new ticket protocol fields or automatic semantic acceptance.
6. Test the documents against **concrete decision scenarios**: TASK-108-style worker `incomplete` despite pending actionable subtasks; a valid short unit with continued execution possible; real blocker; imminent shutdown; zero-delta retry; worker `completed` with stale contradictory audit; red/pending CI; absent report artifact; consecutive rework; safe workflow moves; installed versus running runtime; autonomous diagnosis and escalation. Distinguish evidence visible in OpenCode/Devlegate traces from hypotheses about model intent. Include a concise decision matrix showing expected worker claim and reviewer disposition.
7. Assess information architecture: short role entrypoints versus normative policies/references/checklists, structured machine-checkable contracts where warranted, prompts/examples, duplication, drift prevention, versioning, generation ownership and token/context overhead. Compare viable formats instead of assuming more `SKILL.md` prose is always better. Include a minimal, testable prompt-only change candidate and a separate DoD/architect guidance candidate; do not conflate their effects in evaluation.
8. Propose a coherent revised prompt/skill/ticket structure and migration/validation plan with testable behavior scenarios, backward compatibility for pre-DoD tickets, source-of-truth and exact project-template regeneration pathways, and small prioritized follow-ups. If later implementation is approved, provide a controlled evaluation plan comparing otherwise-similar executions on real tickets, tracking honest outcomes, reviewer findings, tool calls, tokens/cache usage and work re-read overhead. Avoid treating the historical TASK-108 sequence as an independent A/B trial.

## Boundaries and acceptance
- **Audit/report first.** Do not modify packaged worker prompts, generated/materialized `SKILL.md`, ticket parser, live service behavior or workflow machinery within TASK-087. Do not manually edit generated skills. Any implementation or migration must be separately authorized/scoped following this audit.
- Respect the completed TASK-094 review-feedback binding, prompt-byte provenance and existing safe regeneration/upgrade contract. Do not revert working rework feedback delivery, change admitted execution prompts, or silently replace customized project materials.
- Do not introduce automatic reviewers, per-DoD persistent workflow states, new worker outcomes, autonomous prompt rewriters or a broad role system by assumption. Such additions require demonstrated need and separate design.
- Deliver an **evidence-linked gap analysis**, precise proposed worker/core/directive wording, proposed architect/reviewer changes, DoD Markdown example for a realistic ticket, a machine-versus-semantic responsibility matrix, role decision tests, and prioritized small follow-up tickets.
- Source-of-truth location and regeneration path must be explicit. Recommendations must preserve role separation, owner authority, CI and exact-checkpoint provenance, and the distinction between honest worker claims and independent acceptance.
- Backlog only, pending stabilization and explicit scheduling.
