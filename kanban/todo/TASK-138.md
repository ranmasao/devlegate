## Problem and reproduced sequence
TASK-134's last **reviewed** worker generation was `0c944f7c8bb741a4a367c95c4cfc10d0`, rejected with a valid immutable `devlegate-review-v1` artifact in control commit `28423e3` (`review → todo`). The next worker execution `3cb61e2d366042aeab97caf3f4702ece` was **failed**: `egress_ok=true`, but `transport_ok=false` due to an oversized OpenCode JSONL event. Its checkpoint `7c8274a837bd5579b3ac607bd570ff8d14e5016b` was preserved on `devlegate/work/TASK-134`; it did not enter `review` and has no review disposition. The ticket was later deferred `todo → backlog` at `36d4ef8` and returned `backlog → todo` at `ca394d4`. Following removal of an unrelated stale retry gate, the owner refused to launch with `cannot bind curator feedback for TASK-134: review backlog disposition is malformed`.

The current `review_provenance._transition()` treats a `backlog → todo` move as valid only after `review → backlog`, and raises even when a previous valid `review → todo` was followed by a later deferral. In addition, `ServiceEngine._latest_reviewed_rework_report()` accepts the newest report with `egress_ok=true` even if `transport_ok=false`, allowing a failed infrastructure execution to be mistaken for a completed reviewed generation.

## Goal
Support an explicitly proven pause/requeue of a `todo` task after a failed execution, **without fabricating review attribution, treating failed transport as a reviewed result, losing the accepted feedback binding, or changing retained execution resources**. Keep strict immutable review/worker provenance and fail-closed safety when the worker delta or its ownership is uncertain.

## Implementation contract
1. Separate `failed` and `reviewable/reviewed` execution lifecycle identities. A worker with `transport_ok=false`, or without a genuine `review → todo/backlog` disposition for its exact generation, must never become the source of curator review binding merely because `egress_ok=true`. Prove the correct reviewed generation using exact ExecutionReport identity, publication, review artifact and Git ancestry rather than report filename order.
2. Extend the disposition proof to recognize the deliberate `review → todo` (with immutable review) followed by `todo → backlog → todo` deferral/requeue, potentially with failed attempts in between. Verify expected old/new paths, identical canonical ticket blob, first-parent ordered transitions, no conflicting review publication, and exact reference to the review artifact. Do not generally accept arbitrary `backlog → todo` or a bare missing review.
3. Handle intermediate failed worker checkpoints explicitly. Decide, with durable generation/ownership proof and appropriate CAS/exclusive-owner boundaries, whether the earlier reviewed rework delta can be resumed or the later failed worker's published delta can be safely preserved/continued. **Never silently drop, overwrite, or relabel the `7c8274a...` checkpoint; never invent a new curator review of the failed execution.** If its resource identity or continuation is ambiguous, refuse with a precise actionable recovery reason instead of launching an unsafe fresh worker.
4. Preserve recovery, restart, previous review binding, ticket/worktree/submodule state, Git control lineage, historical reports and refs. Ensure the operator can resume a proved generation after the underlying OpenCode transport bug is repaired. No generic protocol weakening, manual rewriting of historical review files, or task-specific production exceptions.
5. Add deterministic isolated real-Git regressions for the exact TASK-134 sequence, valid `review → backlog → todo`, ordinary direct `review → todo`, multiple rework cycles, failed `egress_ok=true/transport_ok=false` generation, missing/modified review artifact, altered blob, out-of-order/ambiguous transitions, remote ref drift, missing/dirty worktree, and restart. Assert the recovered agent receives the correct historical curator feedback and that no previous checkpoint or execution evidence is rewritten.

## Boundaries / acceptance
Do not rewrite the published control history, delete a failed execution, weaken Git/CAS or worker-ownership proof, or alter actual TASK-134 resources while implementing this fix. Stdlib-only runtime, no migrations or compatibility scaffolding; use disposable test repositories. TASK-137 separately addresses the stale-failure scheduler/retry barrier; neither fix may disguise the other's failure. The real `review → todo → failed → backlog → todo` scenario must reach a safe, explicit continuation decision after both fixes. Focused tests, configured exact-checkpoint CI and a short documented recovery contract are required.
