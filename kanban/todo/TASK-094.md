## Milestone
Devlegate 0.5.7 — **critical review/rework feedback-loop correctness**, follow-up to completed TASK-077 and TASK-083. Schedule before further TASK-092 rework or architecture backlog; do not edit or preempt an admitted worker execution. This ticket does not depend on TASK-092.

## Incident and demonstrated contract gap (2026-10-20)
TASK-092 has undergone eleven worker executions with repeated review instructions to repair the same five Git submodule worktree-removal regressions. Curator reviews were stored independently under `reviews/TASK-092/<execution-id>.md`, while the active ticket specification remained unchanged. Inspection of `release/0.5.7` shows `runtime.py` constructs `build_worker_prompt(WorkerPromptInput(assignment=selected_ticket.body, directive=directive))`. `worker_prompt.py` renders only `Core Worker Contract`, `Work Directive`, and `Assigned Work`; the `rework.txt` directive refers to supplied feedback without actually receiving it. Workers run in product execution worktrees and must not require access to control-plane files. An agent's ability to discover Git history is NOT an acceptable feedback delivery mechanism.

Earlier TASK-083 required focused curator feedback (requirement 9 and regression 9), but its historical handoff used temporary ticket-embedded references to independent review files pending first-class injection. TASK-077 explicitly reserved separate review history to prevent obsolete review iterations from bloating active ticket context. Current generated `skills/architect/SKILL.md` and `skills/reviewer/SKILL.md` templates still recommend appending hardening requirements to ticket specifications. These contradictions must be closed end to end, including already-initialized projects.

## Goal
Make the **latest valid applicable curator review** a deterministic, bounded, provenance-checked input to a new REWORK worker prompt, independent of ticket text and without exposing control-plane mutation authority. Align architect, reviewer, worker contracts and already materialized/generated project artifacts so a deployed runtime upgrade takes effect reliably and safely.

## Required behavior

1. **Audit actual prompt and artifact pathways before editing.** Trace ticket selection, rework admission (TASK-083), review storage and lifecycle provenance, `WorkerPromptInput` / `build_worker_prompt`, packaged `default_templates/prompts/{core_contract,fresh,resume,rework}.txt`, `WorkerSupervisor` stdin delivery, project `.devlegate/templates/artifacts.toml`, generator/source templates `.devlegate/templates/skills/{architect,reviewer}/SKILL.md.tmpl`, generated `skills/{architect,reviewer}/SKILL.md`, package-provided defaults and runtime upgrade/init/regeneration commands. Identify the exact source of truth and which templates are baked into the installed standalone bundle vs copied into projects.
2. **Select only applicable review feedback.** Resolve the current REWORK generation's latest independently published, genuine curator review artifact for the **immediately preceding completed execution** (or the latest valid review disposition carried across review->backlog->todo), bound to exact ticket ID, execution ID, verified lifecycle report/checkpoint and control revision. Verify the expected review->todo rework event and prevent stale prior-generation reviews, wrong-ticket documents, untrusted filenames, tampered/ambiguous history or ordinary unrelated control commits from being silently selected. Reuse existing Git lifecycle/provenance infrastructure rather than introducing heuristic “newest file by name/time” selection or a large new review framework. Define a small, explicit attribution/disposition convention for independent review artifacts if required and a compatible transition for existing historical files.
3. **Clear failure semantics.** FRESH has no review feedback; REWORK with no review artifact needs an explicit justified legacy/compatibility path only if a proven curator rework request exists, otherwise **fail closed with actionable diagnostics** instead of launching a worker that is told to use feedback it never received. Handle malformed, missing, unreadable, conflicting and stale feedback distinctly. RESUME of an interrupted execution must use the same admitted review binding and prompt, not automatically switch to newly edited/latest review. Backlog deferral and daemon restart must not lose the binding. Review edits during active execution must not silently change the worker assignment or create a new generation.
4. **Compose a bounded, structured worker prompt.** Keep `Core Worker Contract`, explicit FRESH/REWORK/RESUME directive and canonical `Assigned Work`; add `Current Review Feedback` only when a verified applicable review exists. Preserve source review content verbatim rather than LLM-summary synthesis, with clear provenance/version reference available to the engine and optional concise non-secret agent-visible source label. Treat curator text and ticket text as task data, not a channel to override execution safety constraints; delimit both safely (existing fence strategy). Do not concatenate the entire historical review archive or ancient resolved instructions. If feedback exceeds safe configured limits, fail visibly or use a deterministic explicit selection policy, never silently truncate mandatory blockers.
5. **Prompt observability.** Permit independent inspection of the exact UTF-8 prompt bytes the engine actually submits to OpenCode, bound to execution ID, directive, ticket generation, review artifact identity/checksum and an appropriate SHA-256. Choose an access-controlled runtime-local durable diagnostic/artifact or a safe opt-in operator command; never publish hidden state, credentials, user secrets, private paths or large prompts to public control Git, systemd journal or status by default. Ensure logging can confirm the bound review ID/hash without logging the entire prompt. Distinguish prompt constructed, prompt sent, and subprocess delivery failure; do not claim delivery when stdin write fails.
6. **Align role contracts with actual ownership.** Review and make the smallest necessary changes to worker core/rework text and architect/reviewer source templates: reviewer stores current feedback as a **separate review artifact** with explicit association to completed execution, keeps the ticket's canonical requirements stable, and makes a correct workflow move; architect authors standalone ticket requirements and handles only real spec changes; worker reads the injected current feedback and retained code before making changes, does not attempt to read/control `devlegate/control`, commit, push or alter workflow. Define what happens when a reviewer needs to amend canonical requirements (separate explicit guarded spec revision vs ordinary rework comments). Remove misleading instructions to append review changelogs or to rely on manual `git show devlegate/control:reviews/...` from execution worktree. Coordinate with TASK-087 role-skill audit: this ticket fixes the **proven blocking contract mismatch**, not a wholesale skill redesign.
7. **Installed runtime and materialized project migration.** Implement the minimal safe mechanism that makes updated bundled prompt templates effective on the next worker launch after upgrading the **running service**, and brings existing project-generated architect/reviewer skills into sync with corrected source templates. Explicitly distinguish managed generated artifacts from project-owned overrides; avoid overwriting user modifications, non-atomic rewrites, changes to in-flight/admitted tickets and uncontrolled mutation of control Git. Define version/managed marker/hash or equivalent for generated templates and drift detection; support idempotent regeneration or explicit upgrade/migration with safe diagnostics and clear operator command when automatic migration cannot be proven safe. A plain product package install without service restart does not magically replace an already-running Python process. Document defaults, upgrade procedure, rollback, and how legacy materialized files are detected.
8. **Bound implementation.** No broad rewrite of Git/recovery, no change to worker Git permissions/containment, no auto-acceptance, no history deletion or rewriting old review artifacts, no incident-specific TASK-092 fix, no speculative new role framework. Keep the review selector, prompt renderer and artifact materialization responsibilities cohesive and testable, not added indiscriminately to `runtime.py`.

## Required regressions

1. Real-Git workflow: completed execution -> independent review artifact -> `review -> todo` -> next REWORK. Assert the **actual prompt bytes written to the worker stdin** contain the exact latest applicable feedback and the ticket spec, but none of the older resolved reviews. Assert a correct mode/identity is selected, not RESUME.
2. Two consecutive rejected generations: review #1 then review #2; second REWORK uses #2, not #1 or whole-history concatenation. Direct review->todo and review->backlog->todo behave equivalently.
3. FRESH uses canonical ticket and no spurious review; same-execution RESUME after daemon restart preserves previously bound feedback/prompt; a later review publication cannot mutate that binding.
4. Missing/malformed/conflicting/forged/wrong-ticket/wrong-execution review, changed control HEAD, and failed Git observation must block unsafe admission with actionable diagnostics and no subprocess launch. Include a legitimate legacy rework state according to documented migration policy.
5. Worker worktree cannot read or mutate private control plane and still receives feedback correctly through stdin.
6. Prompt fencing preserves literal content and cannot erase or overwrite safety contract; stable deterministic hash/bytes for same binding; transport write failure is reported separately; diagnostic artifact/command respects confidentiality.
7. Fresh project init and upgrade of an **existing project with materialized** `skills/architect/SKILL.md`, `skills/reviewer/SKILL.md` and `.devlegate/templates`: corrected guidance becomes effective via documented supported path, without destroying intentional overrides. Repeated migration is idempotent, interrupted migration recoverable, older customized files generate an explicit conflict or manual action.
8. Verify CLI-installed and standalone packaged-runtime scenarios as well as source install where applicable; exact-checkpoint full CI pytest/coverage and Ruff green. Include one end-to-end TASK-092-style scenario showing the latest review's five submodule regressions appear in the next worker prompt without appending them to the ticket.

## Acceptance criteria

- The actual OpenCode input for REWORK demonstrably includes the correct latest curator review (when present) and no obsolete history; decision is traceable to immutable control evidence.
- New and previously initialized projects can use the corrected architect/reviewer/worker protocol after a documented runtime upgrade, with safe preservation of project customizations.
- Runtime upgrades and recovery preserve deterministic prompt/review-generation binding and existing fail-closed Git, owner, WAL and execution-state invariants.
- Focused tests and full exact-checkpoint CI green; reviewer validates both worker-visible prompt and deployed/materialized templates, not only function-level string assembly.
- This critical ticket is reviewed before resuming repeated TASK-092 rework cycles; TASK-087 remains the separate broader skills architecture audit.
