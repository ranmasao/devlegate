## Milestone

Devlegate 0.5.7 — **finish the ordinary deferred failed-execution continuation promised by TASK-145**, specifically the real TASK-134 history. This is narrowly scoped hardening of the integrated feature, not a new historical-repair workflow. The user wants TASK-134 to resume next, without manual SQLite repair or a new operator command.

## Goal

A previously reviewed execution followed by a transport-failed checkpoint must be eligible for normal `backlog -> todo` continuation **when independently and safely proven**, even if its transient `failed_executions` SQLite metadata has disappeared and the unchanged ticket has been deferred/requeued multiple times. Preserve genuine curator feedback and the **later failed code checkpoint**, and keep all unsafe cases fail-closed with precise diagnostics. Make read-only `status` agree with actual pre-worker admission.

## Required behavior

1. **Admission without a transient failure cache, with a real trust boundary.** Derive the candidate failed generation from unique, immutable, exact Git-control report/lifecycle history, not a report filename sort or invented SQLite entry. Verify report authenticity, exact failed control publication, real post-failure first-parent deferral and subsequent requeue, unchanged canonical ticket blob and currently runnable ticket, and the preexisting genuinely reviewed predecessor (if present). If an existing local failure record agrees, use it as additional evidence; if absent, do **not** synthesize it or permanently weaken another retry gate. If a nonempty record conflicts, current observations are ambiguous, or continuity/ownership cannot be proven, fail closed with a **specific** reason. Explain exactly which evidence is needed; never treat the historical report alone as proof of live worktree ownership or a synthetic BOUND record.
2. **Finite-state repeated dispositions.** In the failed-continuation admission path, accept one or more complete `todo -> backlog -> todo` cycles after the failure (including repeated cycles), allowing independent changes to other tickets/files in the same commit. Preserve a strict first-parent, single-current-location, unchanged-blob and legal transition invariant for TASK-134 (generic for any ticket). Reject changed content, missing/duplicate ticket, unexpected state transition, missing final requeue, divergent/merge ambiguity and ambiguous report attribution. Requeue only grants permission to **attempt** safe continuation, not permission for destructive Git changes.
3. **Curator review provenance across unrelated changes.** Adapt `review_provenance._transition` as necessary so the original reviewed generation and **exact immutable review artifact co-published with its review disposition** remain correctly bound across multiple later deferrals, requeues and independent ticket commits. The review publication itself must stay strictly attributed and immutable; reject missing, malformed, stale or misattributed feedback. Do not turn the failed generation into a reviewed one or inject stale feedback.
4. **No regression of safe workspace handling.** Once admitted, invoke the existing TASK-145 rework preparation: preserve all 18 (generic: full linear) failed-code commits, original checkpoint/evidence refs and genuine feedback; on advanced product base use the existing one-time, restart-safe candidate transplant with pin/CAS/remote lease. Check current managed worktree, registration, dirty/locked/symlink/submodule/foreign topology, worker absence, refs and other competing intents **before any effects**. Do not infer resource ownership from branch name/SHA/path alone; if real current worktree state cannot be independently proven, block precisely without losing history. Avoid production special cases for TASK-134.
5. **Honest status and restart semantics.** Read-only `status`/`plan` must not advertise `run-worker` when the next ordinary owner iteration will deterministically refuse the same candidate at the missing-metadata/history gate; present an actionable, stage-specific blocked reason. Inspection has no Git mutations or SQLite writes. Repeat polls/restarts must not discard reports, corrupt refs or start duplicate workers. Preserve unrelated failure metadata (including TASK-088), existing normal rework, current-generation retry, other scheduler tickets and reconciliation behavior.

## Acceptance criteria

- A fully disposable real-Git scenario matching the specific incident: genuine reviewed execution + attributed feedback, later transport-failed execution with >=2 checkpoint commits, **absent** `failed_executions[ticket]` in persisted SQLite after a later clean idle state, >=3 independent defer/requeue cycles with other ticket additions in deferral commits, advanced clean product head, unchanged ticket blob. Ordinary scheduler creates a fresh execution without a manual command, carries full failed delta **once** and injects the genuine reviewed feedback. The old failed report/review bytes and checkpoint remain intact and reachable.
- Same scenario with a matching failure metadata record also works. A conflicting failure metadata record fails closed. Source histories lacking independently proven lifecycle, valid deferral/requeue, review attribution or current resource ownership block without modification. Do not fake an old `BOUND` or grant generic reset/cleanup authority.
- Repeated cycles and unrelated control commits do not weaken the strict review publication/checkpoint proof, single-ticket blob invariance, or ownership/ref/remote lease checks. Existing one-cycle same-base and advanced-base TASK-145 tests remain green.
- For safe, independently provable cases, read-only status and ordinary scheduler agree; for unsafe cases, both expose specific actionable blockers rather than the generic `lacks a safe current admission` message. No worker launched on refusal.
- No new CLI/IPC command, repair flag, migration, manual SQLite mutation, separate ticket, replacement ticket text, or broader Git-rewrite subsystem.
