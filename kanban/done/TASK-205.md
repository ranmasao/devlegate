## Milestone

Devlegate 0.5.8 — prepare for independent architecture audit and follow-up maintenance.

## Goal

Permit an authorized curator to move a completed implementation ticket from done to todo with the same ticket ID and optionally rewritten specification, admitting a fresh implementation cycle against the current product revision without discarding the previous integration or its immutable evidence.

## Context

The current workflow treats done as terminal (tickets.py WORKFLOW_TRANSITIONS). Historical reports, reviews, accepted checkpoints, cleanup and recovery are tied to execution/control identities, while the per-ticket work branch and workspace names may be reused. Reopening is new work, not retry, reset, RESUME or REWORK of the completed execution. TASK-204 and TASK-191 have real post-integration defects reserved for later reopen; do not implement those fixes in this ticket. The project is self-hosted without a customer base: no runtime data migration or backward-compatibility subsystem is required.

## Required behavior

- Treat an explicit committed curator transition from the unique canonical done path to todo for an ordinary implementation ticket as the authorization to reopen. The move may atomically replace the specification body/metadata with a valid new specification under the same ID, or preserve it byte-for-byte. Existing ticket graph validation and control synchronization remain authoritative. No additional CLI command, mandatory reopen artifact, new ticket ID, hidden hold flag, manual reset, or agent action is required. Do not infer reopen from an unrelated product change, editing a done ticket in place, ambiguous/duplicate paths, or a failed/abandoned disposition. Abandoned and abandonment-analysis lifecycle semantics remain unchanged.
- A valid reopening begins a fresh implementation cycle. Admit normal FRESH work from the current eligible product HEAD and current committed ticket specification when its dependencies are satisfied. Historical done/accepted/review/retry/rework/automatic-retry/reset/reconciliation state must not authorize or block the new cycle merely because it shares the ticket ID. Establish the current cycle boundary from existing canonical history and execution/control binding wherever sufficient. Reuse existing owner preparation, retirement and publication contracts; do not recreate a parallel transaction framework, introduce a generic generation registry, or blindly clear state that still owns a real pending effect.
- Preserve old integration in product history, previous execution reports, reviews, attributable checkpoint evidence, prompt artifacts under existing retention rules and the ticket blackboard. Do not synthesize or mutate historical reports or feedback. Old review feedback is not the current FRESH assignment. Historical exact-execution inspection remains valid; ordinary current-cycle BASE/WORKTREE semantics describe the new work, not a diff starting before the prior integration. No new historical revision selector is required.
- Handle both ordinary post-done cleanup already completed and retained prior-cycle resources/cleanup still pending. Retire/reuse old per-ticket resources only under existing ownership/identity checks; never reset a foreign worktree or overwrite an unproved ref. A legitimate completed historical disposition must not be replayed into the new cycle or retire a new workspace. A genuinely unresolved previous integration/cleanup authority remains subject to existing safe recovery; distinguish it from stale historical facts. Re-observe exact control and resource identities at existing mutation boundaries. Owner alone changes worktree/ref/runtime state.
- Reopening does not undo previously completed dependent tickets or cascade their reopening. A not-yet-completed dependent uses the ordinary current DAG rule: its dependency must currently be done before new admission. Preserve existing admitted-execution safety; no implicit cancellation of unrelated active work or historic reinterpretation of an integrated dependent. Document this distinction.
- Review, accept and integrate the reopened cycle normally; select the current cycle's report/checkpoint even when earlier reports are valid and have the same ticket ID or specification blob. Subsequent review->todo REWORK and failure/retry/restart within the new cycle retain their normal semantics and cannot accidentally bind a previous cycle. Repeat reopening after the new integration using the same mechanism. Keep the existing terminal log-follow contract (a follower that already ended at done is not resurrected).
- Audit all relevant consumers of historical same-ticket evidence and canonical transitions (scheduler/admission, review provenance, accepted selection/integration, reset/retry, cleanup/retirement, inspection/Change Explorer, logs, source packaging, abandonment targeting). Change only those that incorrectly treat a prior completed cycle as current authority. Record actual affected paths and why unaffected paths require no modification. Update durable workflow documentation and role instructions as needed. Avoid widespread speculative hardening; prefer the weakest sufficient cycle discrimination based on existing facts. No actual real-host update or live control mutation by the worker.

## Acceptance criteria

An ordinary completed implementation ticket can be explicitly moved done->todo with revised or identical specification, then run, reviewed, accepted, integrated and reopened again without a new ID, operator recovery steps for already settled effects, historical evidence loss, previous product rollback, or stale authority crossing cycles. Existing completed dependents remain completed; newly admitted dependents obey the current graph. Prior and current exact execution evidence remains separately attributable. No new public command or special persistent transaction machinery unless a concrete existing boundary demonstrably requires it; explain any unavoidable addition in the report. Preserve existing fail-closed mutation authority and no-migration scope.

## Required regressions

1. Real disposable Git control/product + owner workflow: integrate T, advance product with unrelated changes, atomically move done/T to todo/T with revised specification, admit FRESH at current product HEAD, verify no old review injected, prior product change retained, new checkpoint/report/current acceptance and second done. Repeat with unchanged specification and zero-delta result. Assert historical reports/reviews/checkpoints are intact and current admission binding distinct.
2. Exercise cleanup completed and safely retained previous-cycle resources; restart/replay around reopening and new admission, including an old completed reset/integration record and pending cleanup. Prove stale cleanup/acceptance cannot retire or integrate the new generation, and foreign/ambiguous owned resources still refuse safely. Use existing transaction regressions for unchanged guarantees rather than duplicate entire matrices.
3. Reopen a prerequisite with a done dependent and a todo dependent: done remains done; new todo dependent waits until prerequisite done again. Preserve graph validation, duplicate ID refusal, ordinary review and abandoned boundaries.
4. New-cycle REWORK and retry with previous-cycle reports present: only new-cycle evidence authorizes continuation and accepted integration. Exact historical inspection and ticket blackboard survive; current BASE/WORKTREE uses new base. Cover relevant source selection/log/cleanup paths where the audit identifies current-cycle assumptions. No historical-data migration.
5. Focused tests, lint, diff check and exact-checkpoint hosted CI; document an external curator move procedure using normal committed control transitions, not a new product command. Do not perform it on actual TASK-204 or TASK-191 during implementation.
