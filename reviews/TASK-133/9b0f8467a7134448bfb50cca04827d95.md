## Architectural assessment — overengineering

**Risk is real, and some previous review guidance helped cause it.** The cumulative implementation now contains overlapping first-parent ticket-history walks: `amendment_history.observe_ticket_history()`, `review_provenance.deferred_amendment_history()`, and `ticket_reset._reviewed_spec_changed()`; owner control-descendant adoption additionally invokes one of them. They have different recognition semantics, duplicate Git subprocess work, and will be harder to keep consistent than a single narrowly defined provenance boundary. This is not an instruction to refactor everything immediately: establish the functional contract first, then consolidate/remove redundant scans only where safely proven.

The old runtime already has `_sync_control()` fast-forward/observation, `load_ticket_store()` ticket parsing/validation/cycle checks, `TicketStore.runnable` dependency scheduling, immutable `execution_control_head` and selected body/dependencies, and `_control_descendant_adoption_error()` eligibility/body checks. Existing `test_dependency_state_change_on_control_changes_plan` and `test_bound_pending_generation_blocks_changed_ticket_content` cover important parts. **Do not write a second schema/DAG engine or a second amendment-specific scheduler.** Demonstrate whether ordinary edits already work through this machinery; implement only missing admission guards.

Edit→revert over an intermediate control commit is not automatically a corruption of a bound worker: if the worker could only receive the snapshot at its admitted control SHA and no intermediate amended spec was admitted, the worker's specification did not change. The canonical ticket does request strict history validation, so do not silently waive that requirement; however, additional independent scans and adversarial hidden-mutation tests beyond the actual admission threat model are poor priorities. Explicitly separate a relevant authority/snapshot race from a harmless historical intermediate commit. If the specification's guarantees themselves are excessive, escalate that as an Architect-level requirements question rather than broadening REWORK ad infinitum.
