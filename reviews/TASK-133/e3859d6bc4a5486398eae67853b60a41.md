## Primary functional outcome for the revised specification and next implementation

The intended feature is **deferred application of ordinary Git-native ticket edits**, with the smallest required changes to existing owner admission/review. It must not replicate Git history management or turn Devlegate into a comprehensive hostile-Git forensic checker.

1. **Unbound ticket.** The curator can change the existing `backlog` or unbound `todo` Markdown at the same canonical path/ID, commit and push to `devlegate/control`. On normal owner sync, existing ticket parsing, dependency DAG validation, runnable selection and admission bind the **exact current Git snapshot/blob**. An eligible new worker starts FRESH with that new text. No amendment command, metadata, generation numbering, extra DB table, custom diff engine or extra VCS abstraction.
2. **Bound or running worker: defer, never hot-swap.** A control-branch edit B0→B1 must neither interrupt/kill the running worker nor change the bound B0 prompt and its execution identity. That worker may complete and persist a checkpoint C0 and report **attributed to B0**. B1 becomes relevant only at the next explicit, safe review/admission boundary. An amendment **alone** never discards already completed work; reset is separately authorized and is not the automatic response to an edit.
3. **Review B0 vs B1.** The independent Reviewer must be shown, or be able to obtain, both original B0 and the current B1, the specification delta, C0, the execution report and implementation evidence. Reviewer must explicitly assess C0 **against B1**: ACCEPT only when B1 is satisfied, otherwise REWORK with preserved C0. Do not silently claim B1 was delivered to the B0 worker, or interpret a review of B0 as approval of B1. Keep normal unchanged-spec REWORK and blob-preserving review dispositions safe. Decide a minimal, deterministic review-publication boundary using already tracked Git identities; do not assume a Reviewer LLM supplies Git SHA values.
4. **Next worker after REWORK.** When an adjustment is required, preserve the previous checkpoint/evidence and base the next attempt on the remaining work with B1, not an implicit destructive fresh start. Future read-only Git diff access can help both worker and Reviewer navigate B0→B1 and code changes; **do not implement Worker diff tools or Reviewer harness tools in TASK-133**.
5. **Trust and separation.** Git supplies object identity, version history and native diffs. Devlegate owns serialized admission, immutable execution binding, state/resource authority, existing safe reset, review attribution and publication preconditions. A Reviewer can be a web agent with Git access **or a future harness agent with no Git access**; the semantic ACCEPT/REWORK judgment must not rely on the agent computing, copying or asserting Git hashes. Internally derive and verify those identities deterministically; the future limited-access Reviewer tools/API are **not** part of this iteration.
