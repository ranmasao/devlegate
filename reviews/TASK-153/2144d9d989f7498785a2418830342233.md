## Causal evidence available without asking the worker to use Git

TASK-102's status-specific `_failure_superseded()` already proved that a
failed ticket left its earlier published state: synchronized clean control,
ticket-specific unresolved intents, first-parent membership, original path
existence and a bounded `git log --first-parent -m --format= --name-only
--no-renames --diff-filter=D BASE..HEAD -- <ticket workflow paths>`.
This proof was about **displaying old failures**, not authorizing retry.
TASK-137 reused the helper for admission, adding the unrelated
`worker_identity is not None` veto, product-state requirements, extra
recovery intents and per-first-parent-commit `ls-tree` same-blob proof.
Consequently a foreign active worker could revive an obsolete status warning.

Those are distinct decisions:
- **Visibility:** whether authoritative published control history has
  superseded the old recorded failure and no unresolved matching owner
  remains.
- **Admission:** whether a worker can safely be (re)started under TASK-137
  rules, product lineage and current resource ownership.

The existing ticket additionally demands conservative handling of deletion
plus recreation, changed ticket identity, missing/dirty/divergent history,
matching uncertain ownership and new current failures. Do not blindly
restore the TASK-102 deletion-only algorithm if it violates these cases.
But do not assume those cases require a second full history engine.

repair against the integrated product base.** Reconsider the retained
third-attempt status helper from first principles, not as a starting structure
that must be preserved.

1. Keep TASK-137's safety semantics for retry/admission. Separate decision
   policies, but seek a **single compact reusable, read-only ticket-history

   Reuse existing local Git observation primitives where appropriate.

   retires T-OLD from both human and JSON current status while T-NEW runs,
   regardless of unrelated product advancement; historical evidence is
   untouched. Matching uncertain worker or pending recovery must still
   keep the appropriate failure visible. Never hide a new failure for the
   current generation.
3. Preserve honest `plan`, explicit retry candidates and real scheduler
   admission: hiding a historical warning is **not** authorization to run.
   Do not create a second scheduler path, migrations, new durable state or

   incremental diff from the previous rejected checkpoint. Remove dead,
