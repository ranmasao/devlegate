# TASK-056 — REWORK: connect the active watchdog to durable stalled recovery and one continuation

## Independently verified evidence

The eighth execution is a valid durable `incomplete` report, with successful process/transport/egress, no questions, base `a48ed50a5b27c380b23e25494a4378fc1f8450ff`, and checkpoint `f3cc15fe8f476355b9e48f0f2c991adf0d9ee896`. The adjacent report confirms that autonomous stall/recovery/continuation remains incomplete. Review of the exact cumulative code and this execution's commit supports the following **real progress**:

- `runtime_state_validation.validate_state_invariant()` now binds a persisted `stalled_recovery` intent or retired marker to the active `agent_running/worker-running` execution, its exact worker identity and containment/launch evidence. An invalid binding is rejected.
- `recover_stranded_execution()` refuses ordinary process-loss reconciliation when `stalled_recovery` exists, rather than silently consuming or normalizing watchdog-owned provenance.
- `ServiceEngine.recovery_retire_worker()` now delegates to the existing supervisor's exact-containment retirement. `WorkerSupervisor.retire()` checks process identity, rejects `indeterminate`, and delegates to `recover_launch(..., terminate=True)`, requiring an `absent` result.
- The added owner-level regression runs a real child process and checks that the runtime-store intent exists before a mocked containment-provider termination is invoked; it also checks that a failed durable write leaves the child alive. Another test rejects replay against a changed execution and accidental generic stranded recovery.

These improvements **should be preserved**. However, the test monkeypatches `containment_provider.recover_launch`; it does not prove end-to-end kernel cgroup retirement or restart-time re-admission. The existing transaction helpers `persist_stalled_intent`/`retire_stalled_intent` still have no live call site in the worker-monitoring loop, and there is no service startup reconciliation path for the persisted intent/retired marker.

The worker reports passing focused owner/containment tests, lint and diff checks; a combined containment and ticket-reset test invocation hit a 120-second timeout, while containment passed separately. Full GitHub Actions CI for the exact checkpoint was **in progress** when reviewed: https://github.com/ranmasao/devlegate/actions/runs/45069646498 . Neither focused tests nor a future green CI alone establishes the missing behavior.

## Primary acceptance blocker and next verifiable action

**Complete the vertical watchdog transaction in the serialized service owner using the existing pieces.** Do not add another standalone persistence, membership, or cleanup helper unless an integration test proves it necessary.

1. **Trigger and revalidate:** expose a machine-local configurable recovery threshold (initial default 600 seconds) alongside the implemented 300-second warning. At the existing owner-thread polling boundary, revalidate the same active attempt, latest monotonic stdout/stderr activity, normal completion/identity and exact owned-descendant evidence before attempting stalled classification. A quiet worker with a proven active child/tool is not eligible; uncertain membership or late output must fail closed or cancel.
2. **Durable intent before effect:** call `persist_stalled_intent()` from the real owner before any signal. If the runtime-store write fails, no watchdog-triggered termination. Once durable, execute `retire_stalled_intent()` using the exact proven cgroup retirement, not a PID guess. Confirm empty containment and keep the previous attempt's `worker_stalled` attribution, workspace edits, checkpoint and report evidence. Avoid a kill-first path.
3. **Restart and admission:** reconcile persisted `intent` and `retired` states on service restart using existing TASK-061 recovery ownership. On uncertainty, block safely. After *proven* old retirement, authorize exactly **one** continuation, including after a restart between termination and the retired-stage durable write. Do not permit old and replacement workers to coexist, restart a completed attempt or silently route a stalled attempt through generic process-loss recovery.
4. **Deterministic context/status:** include a bounded, repeatable verbatim stdout/stderr tail and stable repository-relative changed-path list with explicit truncation in the replacement prompt, with neutral guidance and no LLM interpretation or private execution/PID/state/worktree/cgroup/sandbox details. Expose warning, stalled and recovering operator status without asserting an unproven root cause.

The next strongest evidence is an owner-level execution test that drives the idle threshold into **persist → exact retire → one replacement**, including restart at each durable boundary. New uncalled seam-only tests do not satisfy this milestone.
