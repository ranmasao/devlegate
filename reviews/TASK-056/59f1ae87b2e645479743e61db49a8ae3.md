## Primary blocker: owner-poll errors currently interrupt under a different reason

This execution identified a concrete integration obstacle; the source corroborates it:

- In `worker_supervisor.py`, the worker wait loop invokes `owner_poll()`. Any exception from that callback is caught as an owner-evidence-channel failure and calls `interrupt("operator_abort")`. `interrupt()` sends the process/cgroup termination signal **before** invoking the callback which persists the interruption kind.
- In `ticket_reset.py`, `ResetStop.kind` returns `"ticket_reset"` when `owner._state_write_uncertain` is set; this may cause the supervisor to terminate a worker even though a new stall-intent write was not proven durable.
- The new `persist_stalled_intent()` helper uses `recovery_save_state()` and has no live owner-poll caller. Naively calling it from `owner_poll` means a failed or uncertain state write may fall into the existing `operator_abort`/`ticket_reset` termination paths without proven `worker_stalled` attribution. A test in isolation with a mocked retirement function does not cover these supervisor interactions.

Do not just raise exceptions from `owner_poll` or repurpose `ResetStop.kind` as a watchdog trigger. An uncertain write must halt watchdog-controlled continuation and fail closed, without relabeling an unproven stall as a normal completed attempt.
