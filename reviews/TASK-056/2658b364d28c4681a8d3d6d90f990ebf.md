# TASK-056 — REWORK: connect the write-ahead stall transaction to real worker ownership

## Verified evidence

The seventh execution has a valid durable `incomplete` report, process/transport/egress success, no questions, and exact checkpoint `4f8c037009b88dbd5de2e87541333d6599df0ce0`. Its adjacent report explicitly states that the new transaction seam is not connected to worker supervision or restart recovery.

The incremental code delta adds `persist_stalled_intent()` and `retire_stalled_intent()` in `src/devlegate/recovery_transactions.py`, with five new tests in `tests/test_stalled_retirement_transaction.py`. The first function validates an `agent_running/worker-running` binding and containment ID, then calls `owner.recovery_save_state(..., stalled_recovery={stage: intent, reason: worker_stalled, ...})`. The second verifies the saved execution/worker/containment match, calls `owner.recovery_retire_worker(...)`, then persists `stage: retired`. Tests check save-before-retire ordering, failure on intent-write, rejection of a changed execution, interrupted retirement replay, and retry after the retired-stage save fails. This addresses the earlier persistence-before-signal design obstacle at a *helper/contract* level and should be retained.

**The tests use a fake `Owner`; they do not exercise actual worker signals, containment retirement, durable runtime-store restart, or a replacement worker.** `ServiceEngine` currently exposes `recovery_save_state()` and `recovery_worker_identity()`, but does not implement the new `recovery_retire_worker()` capability or invoke either stalled-transaction function from the service/worker lifecycle. The helper explicitly places fresh-activity checks and serialization obligations on its future caller. Consequently its isolated tests prove neither write-ahead order in the live supervisor nor restart-safe execution recovery.

Full GitHub Actions CI for the exact checkpoint was still running at review time: https://github.com/ranmasao/devlegate/actions/runs/45068724831 . The worker reports passing focused transaction, recovery-boundary, containment, lint and diff checks; this is a claim, not proof of the missing lifecycle behavior. Even a green CI would not resolve the primary blocker.

## Primary acceptance blocker and next verifiable action

**Wire the existing write-ahead seam into the serialized ServiceEngine owner and real exact-containment retirement/reconciliation flow, not another uncalled helper.** Start with a focused integration test whose actual owner boundary records the stalled intent **before** any process signal and refuses to signal/restart if the durable write fails.

1. Add the machine-local configurable recovery threshold (default 600 seconds) to the existing output-idle timer (warning is already implemented at 300 seconds). Immediately before creating intent, revalidate the active execution, currently live worker identity, monotonic output timer, normal-completion race, and genuinely active owned descendants/tools. Unknown cgroup/identity evidence fails closed; last-moment output cancels a stale stall decision.
2. Implement and use the actual `recovery_retire_worker` owner capability through TASK-055 exact cgroup ownership and TASK-061's shared recovery boundary. Persist `worker_stalled` intent in the established runtime store *before* termination begins; if persistence fails, no watchdog-triggered signal. Reconcile an interrupted intent and retired-stage write using actual containment state on restart; require kernel-proven retirement, never infer it from a helper's return, a stale PID, or an unverified saved flag.
3. From proven retirement and preserved workspace/attempt provenance, authorize **exactly one** continuation. Build its bounded deterministic prompt from recorded verbatim stdout/stderr tail and stable repository-relative changed paths; no LLM summary or private identities, absolute worktree paths, internal cgroup/sandbox details, or guessed cause.
