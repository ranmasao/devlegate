# TASK-056 — REWORK: watchdog behavior and safe continuation are not implemented

## Verified evidence

The latest execution report is a valid `incomplete` claim with process, transport and egress success, no outstanding questions, and a durable code checkpoint. Its adjacent report confirms the worker reached its invocation limit before implementing watchdog recovery. The exact one-commit comparison against the recorded code base changes only `src/devlegate/worker_supervisor.py` and `tests/test_worker_process.py`: the supervisor now offers a byte-level stdout/stderr activity callback, including partial JSONL output, and tests this hook against a live subprocess.

This hook is useful groundwork and should be retained. However the call sites merely accept an optional handler; the reviewed change has no service-owned inactivity timer, warning threshold/status, owned-descendant check, stalled classification, safe termination/replacement transaction, persistent stall evidence, recovery context or restart-safe continuation. Consequently the complete canonical assignment is not satisfied. [CI for the checkpoint](https://github.com/ranmasao/devlegate/actions/runs/44994347112) was still in progress when reviewed; CI status is not the primary blocker.

## Primary acceptance blocker and next action

**Implement the actual owner-mediated watchdog recovery and continuation path**, building on the existing supervisor callback rather than replacing it or creating a parallel lifecycle engine.

Connect observed stdout/stderr bytes to an execution-scoped monotonic last-activity state. Evaluate configurable warning (~5 minutes by default) and stall/recovery (~10 minutes by default) thresholds using the existing service/worker supervision boundary. Revalidate inactivity immediately before acting; a proven active descendant/tool belonging to that execution must suppress agent-idle classification. Use only an exact proven execution ownership boundary from TASK-055, not guessed host PIDs.

Once a genuine stall is established, record a durable `worker_stalled` reason tied to the old attempt and reuse the existing owner/recovery transaction flow to retire the old containment, preserve the workspace and checkpoint/report evidence, and authorize one new worker attempt **only after** retirement is proven. On ownership uncertainty, interruption or restart during this handoff, fail closed or resume only from existing durable evidence. Never let old and replacement workers coexist.

## Mandatory dependent implementation and checks

1. **Lifecycle and status:** reset the activity clock on stdout and stderr bytes, cancel on normal completion, surface running/idle-warning/stalled-recovering operator state without guessing provider/network causes, and keep warning non-mutating. Thresholds must be machine-local configurable.
2. **Deterministic recovery prompt:** project a bounded list of changed repository-relative paths and a bounded verbatim stdout/stderr tail from recorded evidence, with stable ordering, encoding and truncation markers. Include neutral continuation guidance only. Exclude internal execution IDs, process IDs, control/checkpoint identities, absolute state/worktree paths and containment/sandbox details. No LLM summary or OpenCode private database/log format.
3. **Owner/transaction regressions:** exercise exactly-on-boundary output, stdout and stderr resets, quiet worker with owned active child/tool, warning and stall thresholds, completed worker cancellation, old-retirement-before-replacement ordering, a preserved changed file, durable stall provenance, no concurrent replacements, and restart in warning/retirement/relaunch phases. Existing retry/force-stop/process-loss behavior must remain unchanged.
4. **Prompt and observability regressions:** verify deterministic output from identical evidence, byte/path caps, truncation, private-metadata exclusion and accurate operator-visible warning/idle stage. Run focused ticket tests, authoritative full CI and Ruff once the missing behavior exists.
