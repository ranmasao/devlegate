## Primary blocking correctness/availability issue

The current fallback does **not** produce the ticket's actual bounded, pageable changed-path inventory:

1. `_worktree()` includes every large tracked/untracked file with the synthetic identity `"worktree:" + SHA256(stat_tuple)`, irrespective of whether its contents equal the compared checkpoint. That identity always differs from a Git blob object ID, so an unchanged large tracked file is present in `changes()`. If `git diff-files` does not flag it, the implementation changes `record.change` to `unknown` rather than avoiding the spurious candidate. **An unchanged 17 MiB file becomes a returned change/unknown in the new regression test**. This is not a faithful list of changed paths; it can consume pages/quota and misdirect the worker.
2. If *any* large WORKTREE file exists, `_unverified_worktree` is set. When the inventory spans multiple pages, `changes()` returns `TOO_EXPENSIVE` instead of even its first authenticated page, regardless of whether the large file is unrelated. The new regression explicitly expects this refusal with 35 small newly added files and one unchanged 40 KiB file. This is a documented partial workaround, not successful pagination.
3. `git diff-files --name-only` observes index vs working tree, while the requested comparison may be BASE/HEAD vs the combined staged + unstaged + untracked state. The inventory must form a complete, validated candidate set for the named virtual base, including staged modifications, removals, modes and untracked names. A stat signature or Git status alone is not proof of stable mutable content; opaque continuation must either bind to a proven observation/snapshot or explicitly fail without presenting a partial response as complete.
4. Large-file `diff()` still ends in `TOO_LARGE` even if the actual change is small. The contract distinguishes file size, patch size and bounded cost. Restore a bounded, verifiable selective reading strategy, for example a Git-assisted candidate inventory with owner-side snapshot integrity plus on-demand content verification rather than hashing the entire worktree for every response. Do not grant arbitrary raw Git arguments or expose Git IDs to worker.
