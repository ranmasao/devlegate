## Explicit curator interpretation: upstream Git ref authority

The initial TASK-151 wording must **not** be interpreted as requiring
mathematically impossible proof of uninterrupted remote-ref identity from
vanilla Git `ref + SHA`. Git's `--force-with-lease` protects the observed
ref value but cannot detect an ABA deletion/recreation with the same value.

For this task, **REPLACE** any demand for absolute uninterrupted remote
identity with an explicit, implementable **operational authority model**:
- A remote ref is eligible only if it is in the owned namespace, its creation
  and relevant later updates are attributable to the precise Devlegate
  execution generation through durable *independent local operation receipts*
  and Git control/evidence history, and the remote value is reobserved
  immediately before a conditional lease-guarded delete.
- Validate that no current conflicting worker, reconciliation, recovery,
  publication, or other owner uses/pins that resource; refuse unowned,
  ambiguous or incompatible observations, missing receipts, unexpected
  ref generations, changed values or remote outages. Record pre/post
  observations for restart and classify a failed/ambiguous deletion as
  `blocked`, not `absent`.
- **Document the threat-model assumption**: other actors with remote write
  permission could perform undetectable same-SHA ABA operations; ordinary
  Git cannot preclude this. Never claim a stronger guarantee. If that
  residual risk is unacceptable for a particular remote, offer a supported
  blocked/manual-authority outcome rather than a silent unsafe deletion.
- Apply equivalent strict per-generation provenance and exclusivity checks
  to code-pinning refs; do not sweep every pin under a ticket name by pattern
  or delete a pin still needed by another execution/recovery.
- Keep the policy narrow to TASK-151; do not build a generic remote
  transactions framework or weaken existing normal accepted-integration
  retirement rules.

This is an explicit curator clarification/override of the original overly
strict acceptance formulation. It does not excuse proving local ownership
or authorizing only the exact intended remote/pin deletion.
