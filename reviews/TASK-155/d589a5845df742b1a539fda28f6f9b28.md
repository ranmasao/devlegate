## Blocking correctness defect — silently omitted staged-only Git metadata

Canonical TASK-155 explicitly requires the live worktree's staged and unstaged source state to be represented, or rejected if it cannot be safely captured. `tools/ticket_source.py::capture` checks unmerged index and compares index bytes/status for *concurrent* changes but does not detect staged-only Git metadata changes that are stable before and after capture:

1. **Staged gitlink change.** `validate_source_submodules(live, selection.head)` validates the submodule against **HEAD**. `inventory(live)` excludes submodule paths taken from `_gitlinks(..., HEAD)` (approximately lines 321–346); `clone_at` and `prepare_submodules` materialize the original `HEAD` pin, not the changed index gitlink. A worktree can therefore have `HEAD:vendor/lib = A`, index `vendor/lib = B`, and checked-out submodule at A. Its Git status shows a staged change; the private snapshot retains A, is clean, and `capture` may falsely classify it as `source_kind=committed`, `wip_digest=null`. No index/status race occurs to trigger the existing checks.
2. **Staged-only executable-mode change.** An index-only `git update-index --chmod=+x path` with unchanged filesystem bytes/mode likewise produces a stable staged status. `file_bytes` derives copied mode only from the working filesystem (approximately lines 302–318); the target clone still matches HEAD, and the index-only change disappears without an explicit refusal or WIP distinction.

Both transitions were reproduced with ordinary disposable real Git repositories: the source index showed the new gitlink/mode and `MM` status while the private clone retained the old HEAD state and was clean. The defect is specifically the stable initial index state being ignored, not an untested concurrent read or a malicious Git rewrite. The present tests exercise staged *contents* followed by an unstaged modification, but do not exercise staged-only gitlink or mode changes.
