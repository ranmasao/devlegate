## Remaining blocking snapshot/provenance defect

Canonical TASK-155 requires the selected live source's staged, unstaged and non-ignored new source state to be captured faithfully or **rejected** if it cannot be represented safely. It also requires a WIP snapshot not to masquerade as an unchanged committed checkpoint.

A stable **staged-only content** change is still silently lost. Consider a regular tracked `source.py`:

```sh
# HEAD and filesystem contain "A"
printf 'B\n' > source.py
git add source.py          # index contains B
printf 'A\n' > source.py  # working filesystem contains HEAD version A
git status --short         # MM source.py
```

I independently reproduced this Git state in a disposable real repository: `git ls-files --stage` identifies blob B, `git ls-tree HEAD` identifies blob A, the filesystem contains A, and a fresh checkout of HEAD is clean. This requires no concurrent writer or malformed Git data.

At the reviewed checkpoint, `validate_index_metadata` (approximately lines 388–424) compares **gitlink identity and mode**, but does not reject the staged blob B. `capture` (approximately lines 450–485) copies only filesystem bytes A into a clone of HEAD A, then tests whether the **private clone** has a dirty Git status. In this case it is clean and the reported `source_kind` remains `committed`, with `wip_digest=null`, although the selected live worktree has `MM source.py` and contains a distinct staged blob. That is an observable mismatch between selected source state and stated build provenance. A staged deletion followed by restoring its working-tree file may have the same class of ambiguity.

The positive staged/unstaged test validates the case where working bytes differ from HEAD; the new tests validate gitlink/mode changes. Neither proves the staged-blob-equals-working-HEAD edge is safe. The existing check of index bytes/status **before versus after capture** guards concurrency, not this persistent initial divergence.
