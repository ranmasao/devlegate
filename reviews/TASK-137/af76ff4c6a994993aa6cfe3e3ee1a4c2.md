# TASK-137 — REWORK: supersession must survive a proven product fast-forward

The implementation is directionally sound: scheduler admission now calls the same first-parent, unchanged-ticket transition proof used by status; retained failures and reports are not deleted; stale effective failures produce an actionable blocked plan instead of a misleading `run-worker`; test coverage includes clean requeue, unrelated control changes, edited ticket and restart. Preserve these changes and their fail-closed intent.

## Blocking regression against the actual TASK-134 incident

`ServiceEngine._failure_superseded()` now requires:
```python
code.local_head == metadata.get("product_head")
code.remote_head == metadata.get("remote_head")
```
The failed TASK-134 report `executions/TASK-134/3cb61e2d366042aeab97caf3f4702ece.json` was bound to product `5b81966afab8eac2d021332c22a04a34361736ef`. The real `release/0.5.7` product HEAD after integrated TASK-136 is `5028a73eadef40a9b4d2930ea28ee1b32ed5e664`. Control has an immutable `todo → backlog` transition at `36d4ef8` and `backlog → todo` at `ca394d4` with unchanged ticket blob, but the new product HEAD comparison unconditionally rejects supersession. The original deadlock remains: scheduler sees raw failed metadata and refuses new work; retry has no current retryable candidate.

The synthetic `test_published_ticket_transition_supersedes_only_current_failure[todo]` never advances the product branch after the failure, so it cannot catch this. The worker's `completed` claim does not satisfy the canonical acceptance test.

## Required focused changes

1. Separate **same-failure explicit retry** (must retain exact current-generation equality) from **a separately proven successor generation** (control ticket state history plus independently proven safe product lineage). Permit a clean, synchronized product fast-forward *when* the old failed product is a proven ancestor and the new control generation is independently justified; reject divergence, dirty state, unobservable refs, rewrite, unproven ancestry, and unrelated product updates without a qualifying ticket transition. Do not make a product HEAD change alone authorize retry or fresh execution.
2. Add a regression reproducing the real two-plane sequence: persist TASK-134-like failed execution at product HEAD A, publish immutable control `todo → backlog`, fast-forward the product to descendant B as another ticket is integrated, publish `backlog → todo` with identical original ticket bytes, restart owner, verify `status`, `plan` and owner admission agree, historical failure/report survive, and the new generation is not confused with retrying the old failed execution. Keep resource worktrees/refs intact. Verify non-descendant product drift is blocked.
3. Add explicit negative assertions for unchanged todo with product fast-forward only, non-FF product rewrite and local/remote divergence. Check the old failed execution remains nonretryable and that current failures still require explicit retry.
4. Preserve the shared owner-validated immutable-control proof, current failure diagnostics, and actor/worker fencing. Do not reach into TASK-138's curator-review/provenance implementation or pretend this ticket alone makes TASK-134 runnable: TASK-138 must still handle the failed-vs-reviewed generation chain.
5. Run focused tests and exact-checkpoint GitHub CI for the final change. At the time of this review, GitHub Actions run 41362430197 for checkpoint `6a9e54e` was still in progress. A future green result cannot correct the missing product-fast-forward scenario.
