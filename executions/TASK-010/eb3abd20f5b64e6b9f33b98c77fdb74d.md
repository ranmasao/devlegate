# Devlegate 0.5.5 runtime coverage review

## Overview

Fresh coverage was generated from the current source with branch coverage enabled and vendored code omitted. The HTML report is `htmlcov/z_2529479955200e8b_runtime_py.html` and was inspected directly, including source markers and coverage.py branch explanations. `src/devlegate/runtime.py` contains 3,516 statements: 2,878 covered and 638 missing. It has 1,586 branches: 1,090 covered, 496 missing, and 418 partial. The resulting HTML headline is 78% line coverage and 69% branch coverage.

The missing logic is not evenly distributed. Most debt is in `ServiceEngine`'s durable state-machine transitions, recovery proofs, lifecycle replay, reconciliation, and polling/error handling. The dominant cluster is `_run_iteration_body` (lines 2675-3079 and its continuation): 86 missing statements, 62 missing branch exits, and 44 partial branches. The next substantial clusters are state validation, checkpoint publication recovery, reconciliation, lifecycle integration, and interrupted-execution recovery. The HTML confirms these are real branch holes, not just a raw JSON artifact: for example, line 2785 has an uncovered fetch-failure exit, line 4390 has a partial zero-delta accepted-integration branch with the annotation that it never jumped to line 4391, and line 5210 has a partial checkpointing/zero-delta recovery branch with the same explicit explanation.

The parallel full-suite run collected 975 tests and produced coverage data for all tests, but four real-service CLI tests failed with `service busy; mutable request was not admitted` under xdist scheduling. This makes the report useful for coverage analysis but means the test run itself is not a clean green baseline; the failures are concentrated in timing-sensitive service admission tests rather than an observed product-file change.

## Largest clusters

1. **Scheduler and product/control synchronization: `_run_iteration_body` lines 2675-3079.** This is the largest cluster by far. Missing paths cover stop-before-admission behavior, detached or unexpected branches, dirty worktrees, fetch and missing-remote failures, pending-sync ancestry/rollback checks, merge failures, divergent histories, and local-ahead/pending execution combinations. The HTML shows fully missing exits such as line 2678 (stop requested), 2811 (pending execution local ancestry proof), and 2786-2797 (fetch/remote-ref failure handling), plus many partial branches. This is high-value behavioral coverage because these decisions protect the product checkout and determine whether work is admitted.

2. **Durable state validation: `_validate_state_invariant` lines 2179-2489 and nested `validate_automatic_retry` lines 2273-2327.** There are 20 missing statements, 18 missing branches, and 18 partial branches in the outer validator, plus seven missing statements and seven partial branches in automatic-retry validation. These paths reject malformed phases, reconciliation identities, retained reports, interruption kinds, worker bindings, and retry metadata. Most are defensive/fail-closed and should not be chased indiscriminately, but malformed persisted state is a recovery boundary, so representative schema tests have high value.

3. **Execution checkpoint and publication recovery: `_recover_checkpoint_publication` lines 5193-5328.** This has 18 missing statements, 12 missing branches, and 10 partial branches. Uncovered cases include invalid pending reports, missing start heads, zero-delta recovery, ambiguous checkpoint history, dirty or changed workspaces, publication races, remote mismatch, and post-publication exactness checks. This is high-risk recovery code: a false positive could publish or finalize the wrong execution, while a false negative should block safely.

4. **Accepted lifecycle integration: `_accepted_execution_report` lines 4231-4356, `_integrate_accepted` lines 4363-4481, and `_complete_accepted` lines 4482-4568.** `_integrate_accepted` has 15 missing statements, 14 missing branches, and 12 partial branches; `_complete_accepted` has nine missing statements and nine partial branches. The uncovered paths include missing/malformed evidence, missing accepted/review transition ancestry, invalid Git identities, stale zero-delta accepted results, product divergence, and exact integration commit checks. The HTML's partial line 4390 branch is particularly important because the zero-delta accepted path is a distinct lifecycle outcome.

5. **Product-base reconciliation: `_reconcile_update_base_owned` lines 6962-7107 and `_reconcile_resume_owned` lines 7109-7260.** These contain 17/16 and 13/15 missing statement/branch counts respectively, with many partial branches. The holes cover wrong target commits, stale or dirty product state, non-descendant targets, changed evidence refs, invalid workspace topology, rebase conflicts and safe abort, remote execution-lineage changes, legacy reconciliation state, and publication races. These are high-value tests because reconciliation deliberately mutates durable state and must prove every identity before doing so.

6. **Interrupted and stranded execution recovery: `_normalize_stranded_execution` lines 7311-7464, `_recover_interrupted_execution` lines 7466 onward, and `_reconcile_stranded_execution` lines 7262-7309.** The clusters have 15, 12, and one missing statement respectively, with 11-13 partial/missing branches in the larger functions. They include worker liveness classifications, incomplete bindings, product/control drift, ticket-body changes, incompatible workspace registrations, invalid checkpoint starts, and ambiguous post-worker stages. The normal successful recovery path is exercised, but adversarial identity and ownership failures remain sparse. This is high risk and should be tested around safety properties rather than percentage alone.

7. **Control-plane attachment/bootstrap: `_attach_existing_control` lines 1898-2023 and `_bootstrap_control` lines 2025-2103.** Together these have 21 missing statements and 16 missing branches. Missing cases cover fetch failure, unavailable remote refs, unregistered or foreign worktrees, wrong branches, missing workflow directories, divergent local control refs, worktree creation failure, staging/commit/push/fetch failures, and conflicting local branches. These are mostly fail-closed transport/topology defenses, but one or two tests per failure family would protect startup correctness.

8. **Polling and operator admission: `_submit_operator_command` lines 881-955, `_run_polling` lines 5865-6052, `_dispatch_operator_command` lines 5842-5863, and status collection lines 6203-6249.** Operator admission has 13 missing statements and nine missing branches; polling has 19 and 12; status collection has 13 and one branch. The HTML exposes rare timing/error paths such as request cancellation, admission timeout, shutdown rejection, worker-vs-scheduler arbitration, snapshot instability, and operator command rejection. These are partly concurrency-sensitive and should be tested with deterministic events/hooks rather than sleeps.

9. **Drop evidence and zero-delta retirement: `_pin_drop_evidence` lines 4762-4830, `_validate_drop_evidence` lines 4858-4901, `_retire_drop_workspace` lines 4944-4990, and `_retire_zero_delta_execution` lines 3846-3907.** These are smaller but have dense partial branching. They validate exact execution/report/evidence identity and remove local and remote execution artifacts. The low execution frequency is legitimate, but the destructive behavior makes focused failure tests valuable.

## Value and risk classification

- **High-value behavioral gaps:** product/control synchronization, checkpoint publication, accepted integration, both reconciliation modes, and interrupted-execution recovery. These determine whether Devlegate starts work, preserves an execution, publishes evidence, or mutates the control plane.
- **High-value concurrency gaps:** operator admission timeout/cancellation, service shutdown while a command is pending, polling recovery after a worker failure, and stable status snapshot retry. These are currently hard to reach nondeterministically and deserve deterministic synchronization tests.
- **Legitimate rare defensive paths:** malformed JSON/state schemas, invalid Git identities, missing remote refs, failed `git fetch`/`push`/`merge`/`rebase`, foreign worktrees, failed state-store access, and failed filesystem operations. Tests should establish fail-closed messages and state preservation, but exhaustive branch pursuit would have poor return.
- **Large unexecuted blocks:** the error and alternate-history portions of `_run_iteration_body`, `_recover_checkpoint_publication`, `_reconcile_update_base_owned`, `_reconcile_resume_owned`, and `_apply_execution_lifecycle`. These are not obsolete based on the source: each protects a documented durable transition. They need scenario tests, not blanket exclusions.
- **Architectural inspection candidates:** the breadth and density of `_run_iteration_body` and `_apply_execution_lifecycle`, together with duplicated proof/recovery branches in reconciliation and interrupted execution, suggest that some paths are difficult to exercise because responsibilities are coupled. Coverage should not be used to delete them, but the concentration warrants decomposition review.

## Highest-value future tests

1. **Pending execution with product history rollback/divergence:** exercise `_run_iteration_body` around lines 2802-2863 and 2811-2845 with a persisted `agent_pending` or `merge_pending` state whose local history is behind or divergent. Verify it blocks without merging or changing durable execution state.
2. **Fetch and remote-ref failure:** force `_run_iteration_body` lines 2785-2797 to observe a fetch failure and a missing remote branch. Verify status 1, diagnostic publication, and no worker admission.
3. **Checkpoint recovery matrix:** target `_recover_checkpoint_publication` lines 5197-5255 and 5284-5328 with invalid report data, missing start head, ambiguous multi-commit workspace history, dirty workspace, and remote publication mismatch. Verify fail-closed behavior and durable stage preservation.
4. **Accepted zero-delta integration:** exercise `_integrate_accepted` lines 4390-4396 with an exact base checkpoint and both matching and stale product heads. Verify matching heads retire the execution and stale heads block without deleting evidence.
5. **Reconciliation update-base success and safe conflict abort:** exercise `_reconcile_update_base_owned` lines 6980-7105 with a valid descendant target, a non-descendant target, and a rebase conflict. Verify conflict abort restores the original checkpoint and leaves reconciliation pending.
6. **Same-base resume lineage protection:** exercise `_reconcile_resume_owned` lines 7114-7259 with changed product/control heads, changed evidence refs, unexpected execution remotes, and the valid publication path. Verify no resume occurs until every identity remains exact.
7. **Interrupted worker ownership classification:** exercise `_reconcile_stranded_execution` and `_normalize_stranded_execution` lines 7272-7450 for matching-live, indeterminate, absent worker, incomplete state, changed product/control, and changed ticket body. Verify live/indeterminate cases block and absent safe cases record the correct interruption failure.
8. **Operator admission timeout and shutdown race:** use events to cover `_submit_operator_command` lines 914-955 and `_run_polling` lines 5895-5949/6013-6049. Verify timed-out commands are cancelled, pending commands are rejected on shutdown, and no duplicate command is executed.
9. **Stable status snapshot exhaustion:** use `_status_snapshot_hook` to force three consecutive mutations through `_collect_status_attempt` and `status_view` lines 6203-6247 and 6731-6748. Verify the last published snapshot is returned, or the expected error is raised when no snapshot exists.
10. **Control worktree topology/bootstrap failures:** parameterize `_attach_existing_control` and `_bootstrap_control` around lines 1903-2018 and 2039-2098 for foreign/unregistered worktrees, divergent refs, and failed create/stage/commit/push operations. Verify startup refuses unsafe topology and does not silently adopt it.

## Decomposition observations

`runtime.py` appears to contain at least four useful future boundaries: (1) scheduler/product synchronization and admission (`_run_iteration_body`, `_sync_control`, product observations), (2) execution workspace and checkpoint publication (`_prepare_execution_workspace`, `_publish_execution_branch`, `_recover_checkpoint_publication`), (3) control-plane lifecycle/evidence replay (`_accepted_execution_report`, `_apply_execution_lifecycle`, `_integrate_accepted`, `_complete_accepted`), and (4) recovery/reconciliation (`_normalize_stranded_execution`, `_recover_interrupted_execution`, `_reconcile_update_base_owned`, `_reconcile_resume_owned`). Status/snapshot collection and operator admission form a fifth boundary because they have their own consistency and concurrency contracts.

The coverage pattern supports decomposition review: `_run_iteration_body` alone has 86 missing statements and 194 total branches, while lifecycle and reconciliation helpers each combine evidence validation, Git operations, durable state writes, and user-facing failure semantics. Extracting narrow proof objects or transition services could make scenario tests deterministic and reduce the need to construct large `ServiceEngine` states. This is an architectural follow-up, not a recommendation to refactor solely to improve the percentage.
