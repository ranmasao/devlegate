## Request to effect

`ipc_server.py:80-244` checks method-specific payload shapes and types on request threads. `runtime.py:1036-1144` translates these into a mutable `OperatorCommand` dataclass (`483-501`) and a SHA-256 fingerprint of canonical JSON (`504-565`); this is a typed envelope with string method and optional overloaded fields, not a discriminated union. The original request semantics are fingerprinted before owner validation can resolve `onto`; reuse of an ID with different method or fingerprint is refused. Cleanup uses `ticket_id="__workspaces__"`, `onto` as limit, and `force` as apply; dry-run has `mutable=False`. Stop/restart use the separate lifecycle route, not these receipts. Public cleanup submission is a separate service entry point; do not infer it from `dispatch_mutation` alone.

At `1168-1269`, submission checks shutdown and drain before receipt lookup, then returns matching durable admission, coalesces an identical pending/active command, or rejects another command or active scheduler as busy. One pending slot is woken for the owner. `_claim_owner_work` (`2565-2580`) atomically chooses it or claims the scheduler; `_run_polling` (`8925-9002`, `9116-9118`) admits and dispatches on the owner and releases the claim in its finally. Hosted repository operations have an owner-thread guard (`971-988`); the process authority lock at `8941-8944` is distinct from thread locks. IPC read views are published snapshots, not fresh authority for mutation.

`_mutable_receipt` validates fields and returns a shallow copy (`2165-2228`); nested result/cohort objects are not deep immutable. Receipt save uses `_save_state` and SQLite replacement; application intent and SQLite WAL are not an atomic transaction with Git, worker processes or remote effects. A store replacement exception sets `_state_write_uncertain` and blocks further saves until restart (`3274-3302`, `3396-3405`). Receipts generally represent accepted admission, not exactly-once completion. For matching ordinary receipts the submitter gets an acknowledgement without redispatch, including after restart; recovery of incomplete effects is method/state-specific. Cleanup explicitly re-observes its bounded cohort. Do not infer global at-most-once effects, nor that every failed admission was effect-free.

## Lock order and contention

Observed edges in this bounded path, not a proof of a complete global lock graph:

* Request submission takes operator RLock then lifecycle RLock for drain, and separately operator then receipt Lock for lookup (`1182-1193`). Owner admission takes operator, calls lifecycle drain check, validation and record; record takes receipt and then state-write RLock during `_save_state` (`2478-2494`, `2235-2331`). Force retry holds receipt across Git checkpoint and state save; cleanup cohort observation also occurs under receipt. Cleanup result copies receipt under lock, releases it, then saves (`2511-2531`), while operator remains held.
* Lifecycle requests take operator then lifecycle (`851-893`); forced abort takes state-write under both, persists interruption/manual retry before signaling (`896-930`). `_save_state` uses a reentrant state-write lock but explicitly rejects reentrant save; its forced interruption check prevents overwriting accepted abort (`3284-3302`, `3365-3395`). Worker supervisor has its own drain/launch coordination. Validation may take snapshot lock through `service_snapshot` (`1276`, `1992`, `2606-2609`); published reads independently take snapshot lock. These observations do not establish absence of reverse edges through callbacks, store, worker or other runtime paths.
* The owner holds operator lock across validation, admission saves, drop/force-retry effects and the complete cleanup sweep. Git fetch, checkpoint, remote operations, SQLite and cleanup can therefore delay other submissions and lifecycle drain. Dispatch of other commands runs after admission lock release, but active-command claim still blocks distinct mutations until owner release. Scheduler claim similarly rejects new requests instead of queuing behind an iteration. Same-ID receipt lookup precedes busy check, but shutdown/drain precedes receipt lookup.

The one-second admission wait (`643`, `1252-1269`) is not a one-second upper bound on the response: after expiry the caller must acquire operator lock. If still queued, it removes and cancels the command and reports not admitted. If the owner has claimed it, the caller sets cancellation and reports the same message; owner checks cancellation before and after validation, but holds the same operator lock throughout validation and recording. Thus the timeout thread may wait until admission/effects have already completed, then set cancellation and report "not admitted" even though a receipt and possibly effects exist. It does not recheck the event after acquiring the lock. Transport loss or store failure can likewise leave an uncertain result. Retry with the same ID and inspect durable state/evidence after service availability; do not treat the timeout text alone as proof of no effect. This is a source-derived race scenario, not a claim that the selected tests reproduced it.

Shutdown rejection removes only pending commands (`2591-2600`); an already claimed admission may finish. The test named `test_shutdown_rejects_operator_command_waiting_for_owner_admission` actually asserts a successful response after stop during paused validation (`tests/test_ipc_owner.py:519-577`), so its name is not evidence that claimed admission is rejected. Lifecycle drain instead serializes with admission through operator lock and blocks new work after it wins. Forced drain must retain durable interruption and provenance before worker signal; changing lock scope or moving I/O requires preserving that linearization and replay contract.

## Regression evidence and gaps

At the baseline SHA, ran:

* `python -m pytest -q tests/test_ipc_owner.py tests/test_force_retry.py tests/test_daemon_cross_layer.py` - 81 passed. In particular `test_retry_request_receipt_coalesces_duplicates_and_survives_restart` (`test_ipc_owner.py:579-654`) proves selected duplicate/collision/busy and reconstructed-engine receipt behavior; `test_mutation_after_owner_commits_iteration_is_definitely_busy` (`338-381`) proves the scheduler claim case; `test_reconcile_update_base_binds_omitted_target_before_effect` (`656` onward) covers target binding and drift. The restart in the duplicate test is an engine reconstruction, not a process-crash proof.
* `python -m pytest -q tests/test_daemon_lifecycle.py tests/test_worker_supervisor.py::test_drain_and_worker_launch_have_one_admission_linearization_point tests/test_control_scheduler.py::test_public_recover_owner_admission_reaches_exact_matching_operation tests/test_control_recovery.py::test_public_recover_owner_admission_is_identity_bound` - 43 passed. These cover selected drain, worker admission and exact recover bindings, not all external-writer interleavings.

Focused future diagnostics should use barriers and real durable state to distinguish queued timeout, claimed validation timeout, receipt-save timeout and effect-before-receipt for drop/force retry; assert the actual response, durable receipt, effect evidence and same-ID replay after a real process loss. Add competing drain and scheduler cases, plus store failure before/after commit and interruption at cleanup cohort/result boundaries, with changed refs and remote uncertainty. Measure time spent waiting for operator, receipt and state-write locks and in Git/SQLite separately; never log sensitive payloads or treat timing as authority. Verify callback lock order, snapshot/state aliasing and worker/store interactions before any lock restructuring. Existing selected tests do not prove a global deadlock-free order, process-loss matrix, exactly-once effects, or all CAS/evidence paths; a future change must reverify its exact integration SHA and the separate recovery audit.
