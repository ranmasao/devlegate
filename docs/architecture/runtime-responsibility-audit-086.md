## Durable state, concurrency and visibility

`_save_state` at 3782-3848 shallow-copies current state, applies fields and phase-dependent clearing, validates, replaces SQLite payload, then changes the in-memory reference. Store `replace` (`runtime_store.py:193-226`) serializes JSON, `BEGIN IMMEDIATE`, increments revision and commits or rolls back; writable connections use SQLite WAL and `synchronous=FULL` (48-71). This database transaction does not atomically include Git, process execution, ticket files or remote pushes. WAL below means the application's persisted intent/stage, not a Git/SQLite distributed transaction. Shallow copying means nested aliases remain significant before serialization.

| Field family | Transition owner and important writers / consumers |
| --- | --- |
| `phase`, `execution_stage`, selected ticket/body/title/dependencies | Scheduler and recovery choose admission and replay; `_save_state` clears selected fields on idle. `_run_iteration_body` dispatches before ordinary admission. |
| `execution_id`, `execution_ticket_id`, branch/path, base/admitted/validated product/control heads, predecessor/transition, remote/start head | Engine binds a particular execution to workspace and Git generations; workspace and recovery check bindings. `reconciliation_transactions.py:560-627` temporarily assigns/restores `owner._state["execution_base_head"]` directly around its operation. |
| `worker_identity`, prompt hash/directive, `pending_execution_report`, interruption kind | Scheduler/worker lifecycle and recovery bind process, prompt and report; `_load_state` at 3305 handles constrained legacy identity and `_save_state` clears transient fields. Forced lifecycle request can save interruption and `manual_retry_required` from the request path (`runtime.py:911-982`). |
| `reconciliation`, evidence/checkpoint and rework lineage | Engine persists reconciliation after pinning evidence (`_persist_product_reconciliation`); reconciliation transaction reads owner private state (`reconciliation_transactions.py:295-645`) and makes state transitions through owner. Local/remote pending stages must survive crash and prove exact ref identities. |
| `accepted_integration`, `automatic_retry`, `resume_required`, `force_retry_authorization`, `manual_retry_required`, `operator_recovery` | Engine lifecycle, retry admission, recovery and integration decide these; their references prevent unsafe retirement. They are not independent boolean flags. |
| `execution_ref_retirement` | `_retire_execution_refs` at 6881 records intent around local delete and restores/clears as appropriate. Re-entry needs occupancy and expected head, not stage alone. |
| `workspace_cleanup`, `workspace_cleanup_cursor`, `workspace_cleanup_event` | cleanup admission/backlog/inventory writes; direct mutations occur at 2558, 5289, 5319, 5424, 6768, some before a subsequent `_save_state`. A failed save can leave changed in-memory state. Inventory and event are observational/presentation-related, not ownership proof. |
| supervision authority | Separate SQLite `supervision_authority` table, written by `runtime_store.py:232-285`, not a key of the runtime payload; separate transactions. |

This is a field-family inventory, not a claim that every nested key or all aliases have been exhaustively proven. In particular mutable reconciliation values obtained from `owner._state` and all indirect capability calls need inspection at any proposed transition seam; `_save_state` is not the only in-memory writer. Git refs, ticket/report files and worker identity are additional durable evidence, with independent commit points.

Hosted repository access is restricted by `_host_owner_thread_id` and `_assert_repository_owner` (1023-1040); `_owned_execution_id` is process-local, assigned on active execution and cleared in `run_iteration`'s finally (3937-3952), not durable authority after restart. `_operator_command_lock` serializes operator/scheduler admission; `_lifecycle_lock` protects intent/drain fields; `request_lifecycle` explicitly nests operator then lifecycle (917-918), and can durably save abort before signaling. `_receipt_lock` protects receipt operations (2218, 2287, 2563); `_snapshot_lock` protects published view pointers (1043-1077, 2696 onward), not all state/Git mutation. Do not infer a complete global lock order from this sample: operator-to-receipt also occurs at 2532-2563, and reentrant lifecycle calls exist. A lock-order audit must include callbacks and IPC request threads before changing acquisition order.

`_collect_status_attempt` (9836) observes store revision and external facts to detect an inconsistent attempt; `_make_execution_plan` (10249) derives policy, and `_publish_status_snapshot` (2748) publishes a view. These do not make remote Git and SQLite one atomic snapshot; re-observation/admission proof remains necessary. `published_drop_candidates_view` (1074-1078) computes from current state under snapshot lock rather than simply returning the cached published candidates: check freshness and concurrent-state guarantees before treating all published views as immutable. `_observe_worktree` (3850) mutates diagnostic fingerprints and logs despite its observational name. Fetch used in product/cleanup observation changes local Git state. These are side effects, not automatically defects.

## Pilot, tests and comprehension

`_validate_state_invariant` is a static method with no direct self access, but depends on `_is_git_identity`, `_worker_identity_from_value`, `validate_automatic_retry`, `ExecutionReport`, `ExecutionReportError`, `ReviewProvenanceError` and `DevlegateError`; inspect these dependencies, their side effects and legacy inputs before asserting purity. Its supported schemas are the current phase/stage and nested payload invariants plus `_load_state`'s constrained legacy worker-identity normalization, not arbitrary old database versions (`runtime_store.py:74-91`). Exact exception type and message are observable diagnostics. Pilot extraction is conditionally plausible only after differential malformed/legacy state tests and a no-I/O/no-mutation check; importing runtime from the validator would defeat the seam. Do nothing is preferable if error and import ownership cannot be isolated without a cycle.

Cleanup has distinct zero-delta, accepted and generic policies; worktree removal, local CAS and leased remote ref retirement require fresh proofs. A generic executor would hide different gates and partial results; retain existing primitives unless destructive-path tests demonstrate a narrower contract. Real Git tests in `tests/test_git.py`, `tests/test_control_workspace.py` and `tests/test_control_recovery.py` cover ref and crash-boundary scenarios; `tests/test_control_cross_layer.py`, `tests/test_recovery_boundaries.py`, `tests/test_service_snapshot.py` and `tests/service_harness.py` provide cross-layer and restart-oriented evidence. Verify each proposed changed path with an actual restarted process where process loss matters, not only a reconstructed engine or mocked runner. Current coverage is evidence of selected cases, not exhaustive crash timing or concurrent external writers.

Concrete comprehension example: reviewed rework needs scheduler admission (`_run_iteration_body`), execution workspace lineage (`execution_workspace.py`), report/review provenance and recovery replay; cleanup needs scheduler cohort, state dependency checks, worktree registration, Git CAS and remote lease. TASK-083's source history shows repeated implementation commits and an integrated commit `15b33fd`; source/test history also shows TASK-076 revisions. This supports cross-boundary rework risk, but the reasons for every review/CI failure cannot be established from source history alone; no private review artifacts were accessed and no model attribution is warranted. Requested historical context-token, re-read/compaction and ticket-difficulty measurements are unavailable from repository source and are not fabricated. A future opt-in study should sample comparable tickets, record unique source/test tokens read and re-reads from authorized traces, cross-file diff and rework, normalize for difficulty and check behavioral/safety preservation; these proxies alone do not establish refactor benefit.

## Backlog slices, proofs and rollback

All are separately schedulable after the stabilization barrier. Priority is risk/value within backlog, not current deployment priority. Each implementation slice should be reverted independently on regression, retaining durable schema/read compatibility and the previous authority path; never roll back by deleting or rewriting live state or refs.

1. **High: evidence-pin race.** `_persist_product_reconciliation` (`runtime.py:8709` vicinity) observes then uses an unconditional ref update, creating a check/write race. Define create-only/CAS handling and matching/conflict observations; prove competing-writer, stop, normal/replay and restart behavior with real refs. Medium risk; revert code path if proof fails, without altering recorded evidence.
2. **High: lock/state transition evidence.** Map every nested state alias, all writers and complete lock ordering including IPC lifecycle requests; exercise failed SQLite save, concurrent forced stop and publication freshness. Deliver invariant table and deterministic race tests before changing authority. Medium risk, observational ticket; rollback tests/docs independently.
3. **Medium: recovery protocol contract.** Declare actual used capabilities and check static conformance plus checkpoint/reconciliation/lifecycle replay. Low runtime risk; do not create a broad facade. Revert declarations if they expose unresolved type incompatibility.
4. **Medium: validator pilot.** First prove dependencies pure and equivalent on representative valid, malformed and legacy payloads, with exact diagnostics and cycle-free imports. Only then separately move validator as immutable input -> existing error/result; keep save, clearing and mutation in engine. Medium risk; restore original validator on differential failure.
5. **Medium: one wildcard family per ticket.** Start IPC or CLI; explicitly import used symbols and make intentional support exports explicit, sort imports, remove only relevant F403/F405/I001 suppressions. Run Ruff on touched files, isolated import and pytest collection, focused domain tests and monkeypatch-sensitive cases. Medium risk because copied names and monkeypatch bindings differ; revert one family at a time. Repeat control and daemon as separate tickets, not bulk rewrite.
6. **Low: narrow remaining lint exceptions.** Separate I001 and E501 tickets: review each occurrence, format safe code and localize justified long literals/import order; run Ruff and affected tests. Keep UP042 and vendor exclusion unless compatibility/ownership evidence changes. Low risk, independently revertable.
7. **Medium: cleanup/snapshot proofs, not extraction.** Instrument fresh status revision/Git observations and cleanup effect ledger; test stale remote, dirty/foreign worktree, changed ref and process loss at each deletion. Only propose extraction if an immutable proof/result contract preserves owner-side revalidation and no new protocol modes. High risk for later implementation; do nothing today.

Comparison: doing nothing preserves tested owner ordering, avoids shared mutable state and new import edges; a thin wrapper without a new invariant only adds indirection; a separate domain transaction is worthwhile only when it owns a closed proof/effect/result contract without private state, circular imports or inflated capabilities. Keep scheduler, `_save_state`, lifecycle and cleanup authority centralized until a smaller seam meets those conditions. Observability should record execution identity, stage, evidence identities, store revision, effect outcome and interruption/replay decision without confusing a published view or WAL intent with proof of a remote effect.
