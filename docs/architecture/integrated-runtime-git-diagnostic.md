# Integrated runtime and Git diagnostic audit

## Workflow recovery capability follow-up

`src/devlegate/recovery_workflow.py` now declares the checkpoint exactness,
reconciliation persistence, and report/state validation calls made by replay.
The corresponding `ServiceEngine` methods in `src/devlegate/runtime.py` forward
to existing owner-held operations; these seams allow the extracted workflow to
invoke them without taking ownership of state or Git. The workflow protocol no
longer declares unused repository attributes or lifecycle application and
finalization callbacks. Those callbacks remain on the engine.

`tests/test_workflow_recovery_contract.py` compares direct owner calls with
protocol methods and checks engine call signatures. Real Git replay coverage
in `tests/test_control_recovery.py` checks exact checkpoint publication,
reconciliation evidence and absence of stale publication, and lifecycle report
provenance. The contract check covers direct calls and parameter shape, not
full static type compatibility or indirect and dynamic calls. These focused
proofs do not establish final architecture approval; the separate recovery
boundary audit and human story gate remain outside this scope. The diagnostic
below records the earlier audit.

## Responsibility and dependency map

| --- | --- |

Host installation, locator and systemd supervision own process discovery and hosting, not Git transaction authority. Operator commands enter `ServiceEngine._submit_operator_command` and `_admit_operator_command`; owner serialization and cancellation are service policy. |
| Scheduling and admission | `run_iteration` -> `_run_iteration_body` coordinates control sync, recovery dispatch, plan/admission, execution workspace, worker, checkpoint and lifecycle. `_make_execution_plan` and `_collect_status_attempt` bind admission to stable observations and worker ownership. `_reconcile_workspace_backlog` schedules a bounded cleanup pass, separately publishing inventory. Keep this cross-domain ordering in the engine. |
| Worker lifecycle | `worker_supervisor.py`, `execution_launcher.py`, `execution_containment.py`, `worker_egress.py`, and `execution_result.py` handle process execution, containment, output and result; the engine binds worker identity and report to the durable execution and decides whether to drain, recover, checkpoint or publish. Do not transfer service ownership into a launcher. |
| State and WAL | `runtime.py:_validate_state_invariant` validates cross-field state; `_save_state` controls phase transitions and `runtime_store.py` persists SQLite state. State stages precede Git effects and are intent, not proof of success. `execution_provenance.py`, `review_provenance.py`, `lifecycle_receipt.py`, and ticket/report handling bind durable identities to control history. |
| Git boundary | `git.py:run_git` executes commands; typed observations such as `resolve_commit`, `remote_ref`, `is_ancestor` distinguish false/absence from failure. | Control workflow | `_sync_control` -> `control_git_workflow.sync_control` -> fetch, observe, optional ancestry and fast-forward, with engine runner and policy callbacks. Attach/bootstrap live alongside it. The engine owns admission and state; workflow owns ordered checkout operations. |

| Recovery | `_run_iteration_body` dispatches by durable stage -> `recovery_workflow.recover_checkpoint_publication`, `recover_lifecycle_report`, or `recover_accepted_integration`; callbacks return to engine for state, observations and effects. `recovery_workspace.py` handles bound workspace inspection/repair; `recovery_transactions.py` handles control lineage and stranded-execution sequencing. |

Zero-delta and accepted cleanup have distinct proof and result policies. |

Dependencies are mostly inward through injected capabilities, but the reconciliation transaction's direct `_state` and `_save_state` references are a concrete reverse dependency on engine internals. A Python import cycle has not been demonstrated. A wide callback protocol is not itself a domain boundary. The recovery workflow's declared protocol omits three methods it actually calls (`recovery_checkpoint_exact`, `recovery_persist_reconciliation`, `recovery_report_matches_state`, at `recovery_workflow.py:122,159,250`); the engine implements them at `runtime.py:10752,10787,10790`. This is a proven static contract mismatch, not evidence of a runtime failure in those paths.

## Executed effects and measurement limits

T1 = local read; T2 = remote read; T3 = mutation, including fetch's local object/tracking-ref writes. Push additionally changes remote state when successful. Numbers below count top-level Git invocations at the named Python runner, not Git's child processes. A transport can spawn `git-upload-pack`, `git-receive-pack`, SSH or credential helpers; hooks and recursive submodule commands can run additional processes and effects. None of those children are included in the runner counts.

Fresh measurement at this HEAD: wrap `ServiceEngine._sync_control` in memory, record arguments at `runtime._git` during the two real-Git cases of `test_control_sync_trace_covers_runtime_observations`, excluding fixture setup and the test's own `git` command. Both passed. Ordered command names:

* Current: `worktree, rev-parse, symbolic-ref, symbolic-ref, rev-parse, show-ref, show-ref, rev-parse, status, fetch, show-ref, show-ref, rev-parse, rev-parse`: 13 T1, 1 T3 (fetch also reads remote), no top-level T2.
* Fast-forward: same sequence followed by `merge-base, merge, rev-parse`: 15 T1, 2 T3, no top-level T2. The fixture advances a local remote; nested transport/hook processes were not counted.

These differ from the older full sync runner measurements of 9 T1 + 1 T3 and 11 T1 + 2 T3 in `GIT_COMMAND_INVENTORY.md:68-73`; those are useful historical snapshots, not current-HEAD counts. The current tracing test checks essential effects and ordering rather than exact totals.

**Keep** `git.py` primitive command builders where they encode typed semantics or mutation parameters; a one-line primitive may be a useful semantic boundary, but a new one-line domain forwarding wrapper without ownership or proof is cosmetic. Keep `control_git_workflow`, workspace manager, and recovery replay as cohesive ordered units. Keep separate normal and replay checkpoint orchestration and the three cleanup policy paths: their preconditions, durable consequences and partial-result handling differ. The historical cleanup investigation explains why a composite executor adds proof-mode adapters while removing little actual logic. Keep `_run_iteration_body`, `_save_state`, admission, lifecycle and accepted integration as owner coordination unless a smaller complete transaction with explicit authority emerges. No generic VCS framework or generalized error layer is justified by this evidence.

The curator should decide whether the evidence race, protocol repair, measurements, or subsequent extraction merit implementation. Completing this diagnostic does not resolve TASK-073 or approve the Git-story architecture.
