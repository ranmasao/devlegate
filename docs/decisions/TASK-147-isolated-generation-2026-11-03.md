# ADR: TASK-147 — isolated generation for deferred failed-execution continuation

**Status:** APPROVED by project owner, 2026-11-03.  
**Scope:** TASK-147 and the underlying generic deferred failure continuation flow; not a new task, not a migration, and not a one-off repair CLI.  
**Authority:** This is the explicit architectural choice requested by the reviewed execution `71f3b09db98f4a109d546213a9c49515` and its immutable review `reviews/TASK-147/71f3b09db98f4a109d546213a9c49515.md`. The owner chose **option A**, ordinary non-destructive automatic continuation. The earlier ticket instruction to reuse the ticket-scoped TASK-145 worktree *by retiring/retargeting it when ownership has been lost* is superseded **only in that unowned-generation case**. All other correctness and trust requirements remain in effect.

## Why this decision is needed

The live 2026-11-03 service experiment at control `c963768dc08b661bfcdbb5f1370d7566d130d36a` showed `plan.action=run-worker` and `plan.ticket.id=TASK-134`, but the owner refused admission: `failed execution continuation lacks a safe current admission`. Runtime SQLite revision `95967` had no `failed_executions["TASK-134"]` and the persisted `execution_*` fields referred to the unrelated latest TASK-147 execution. Product and control were synchronized and clean, phase idle, no worker. The prior failed TASK-134 checkpoint has 18 committed changes, and the earlier genuinely reviewed report has immutable attributed curator feedback. Immutable Git report/provenance proves *source history*, never the current right to retire or retarget its historical ticket-scoped workspace or refs.

## Normative solution and trust boundary

### 1. Admission / generation selection

Keep exact, immutable, first-parent Git-control report publication, preceding genuine review attribution, unchanged task blob through all three `todo → backlog → todo` cycles (with independent ticket changes allowed), and current runnable plan as prerequisites. Reject conflicting **present** failure metadata, ambiguity, non-linear/changed source, forged review, incorrect dependencies, active worker, pending reconciliation, control/product drift, or another owner intent. A *missing* transient failure entry and `execution_*` identifying a later unrelated completed execution are expected, not contradictory historical evidence. They must not be copied into or used as proof of old resource ownership.

Separate **source eligibility**, **existing resource ownership**, and **new generation creation**. No synthetic old `BOUND` or repair state. `status` must preflight the same gates as owner without mutations. Returning `run-worker` is permitted only if the owner can admit a provably fresh, non-conflicting isolated generation; otherwise give a stage-specific block reason.

### 2. New isolated resource namespace

When TASK-145 ticket-scoped reuse/rewrite cannot prove old ownership, create a **new execution ID** with a private, generation-scoped branch and worktree, distinct from all historical ticket-scoped paths and refs. Suggested branch: `devlegate/generation/<ticket-id>/<execution-id>` (Git full ref `refs/heads/devlegate/generation/<ticket-id>/<execution-id>`); suggested worktree: `<execution_worktree_root>/generations/<ticket-id>/<execution-id>`. Equivalent naming is acceptable only if collision-free, canonical-ID validated and persisted. **Do not use** a nested branch such as `devlegate/work/TASK-134/<id>`, because the preexisting `refs/heads/devlegate/work/TASK-134` ref cannot coexist with children under the same ref directory.

Source TASK-134 worktree `.../work/TASK-134`, `refs/heads/devlegate/work/TASK-134`, its remote tracking/publication and historical evidence refs are **read-only** and are not reset, removed, relocated, force-pushed, or retargeted. The source worktree's *current* topology or cleanliness is not an authorization to mutate it. If unowned or dirty it may remain untouched; validate source Git objects and committed ancestry independently. An observed **live or conflicting worker/owner authority** is a hard block, even if old paths are otherwise unused.

A generation-specific branch/path becomes owned only after the serialized mutation owner durably records a new execution-specific intent with the chosen ID, exact control/product source generations, expected target ref absence, expected new branch/path, source report IDs and checkpoint/base, source review binding, and explicit `isolated` mode. The owner then uses create-if-absent / compare-and-swap, path/registration/symlink checks and remote publication leases to create and attach *only these new resources*. Neither a matching old SHA nor a guessed path confers ownership. On restart, reconstruct the authorization from the durable intent and exact observed new resources, refusing conflict; never reauthorize from topology alone.

### 3. Replay failed code exactly once

Treat failed report checkpoint as **immutable Git input**, not as a working tree to be reclaimed. Verify source base→checkpoint is a fully observed *linear* history of the expected number of commits (18 in real TASK-134; generic >=2 in tests), and the reviewed predecessor/feedback are separately bound. If product base equals source base, initialize the isolated branch directly at the checkpoint only when that is consistent with verified ancestry and no duplicate delta. If product base advanced to a proven descendant of source base, use the existing patch-equivalent candidate/cherry-pick utilities or factor their pure candidate-building operation so the full ordered delta is applied exactly once; if already integrated, prove and avoid duplicate replay. Preserve source checkpoint under immutable/pinned evidence before any new mutation and validate output patch equivalence and commit count, not merely the final tree. A conflict or ambiguous ancestry blocks safely with old resources unchanged. Do not duplicate TASK-145 Git rewriting/CAS logic; factor/reuse the existing internals behind a source-vs-destination capability boundary.

### 4. Complete lifecycle support, not only worker preparation

New resource identity is explicit in durable runtime state, worker cwd, report branch/path/heads, publication and remote lease, rework provenance, status/plan, post-worker checkpoint, review, accepted fast-forward integration, restart reconciliation, drop/cleanup and next-generation handling. Any check that currently assumes `devlegate/work/<ticket>` or `work/<ticket>` must either use the exact persisted generation identity or refuse; never silently fall back to or overwrite the legacy ticket-scoped ref. The fresh report must accurately name the isolated branch/path. The old reviewed feedback must go in the new worker prompt, whereas the later failed checkpoint is the **code** predecessor. Do not treat the failed report as reviewed.

Preserve the existing ticket-scoped path for proven, current owner-bound executions. An isolated generation must remain identifiable through later review, accepted integration, failure and rework; a further generation must not accidentally target historical ticket-scoped resources. Existing published review artifacts remain immutable.

### 5. Crash safety / atomicity / idempotence

Define and test an explicit state machine, including: observed/admitted intent → old source pinned → new candidate proved/pinned → new ref created with expected-absent CAS → new worktree attached and validated → remote publication guarded by lease → worker launched → post-worker publication/review/integration. Persist intent **before each effect**, verify actual state on restart at each boundary and advance only with exact evidence. Repeated polls and restarts may reuse a proven owned new ref/path but cannot allocate another worker, reapply an already transplanted delta, drop pins, or retire historical source. No writable operation may touch the old ticket-scoped generation. Concurrent target ref/path/remote changes, dirty/locked/foreign registration, symlink, submodule or competing owner intent fail closed without destructive cleanup. No silent `--force` or inferred owned-history repair.

### 6. Required regressions and acceptance

Build a fully disposable real-Git reproduction of the live TASK-134 case:
1. Authentically reviewed predecessor with co-published immutable curator review; later transport-failed worker with >=2 separate commits; a control report published at an exact immutable commit.
2. Three separate `todo → backlog → todo` cycles with unrelated ticket additions; exact source ticket blob preserved; later unrelated completed TASK-147-like execution overwrites persisted `execution_*` while owner returns to `idle`; `failed_executions["TASK-134"]` absent.
3. Product advanced cleanly; both Git observations synchronized; source historical ticket-scoped branch/worktree remains present, including tests where it is occupied, dirty or unexpectedly registered, provided there is no live source worker. Start the ordinary owner scheduler with TASK-134 in `todo`, **without operator command**.
4. Assert new bound execution has a unique isolated branch/path/owner intent, old branch/worktree/remote/evidence remain **byte-for-byte/ref-for-ref** unchanged, correct 18-commit-shaped delta is present once and genuine earlier feedback is injected; report/review attribution and accepted integration can complete.
5. Verify live IPC status/plan and actual owner agree before admission, after restart at each durable stage, during workers, on block and after completion. Status and preflight never create refs or write SQLite.
6. Negative cases: falsified/missing reports or curator review, ambiguous/merged source history, ticket blob drift, missing ancestry, conflicting nonempty cache, active worker, competing state/reconciliation, changed control/product/remote, wrong branch/path, target ref already occupied, dirty/foreign/locked/symlinked new worktree, submodule mismatch, candidate conflict, lease race, startup crash at each transition, repeat polls. All unsafe paths must preserve original reports, reviews, checkpoints and old refs, not create workers, and give actionable blockers.
7. Preserve TASK-145 normal-current-owner tests and earlier TASK-147 repeated requeue parser; run focused pytest, Ruff and exact-checkpoint full CI. A green existing negative-only test is not completion.

### 7. Scope and handoff

No TASK-134-specific production conditional; no new CLI/IPC mode, operator approval flag or interactive recovery command; no migration/compatibility framework; no new unrelated hardening ticket. Keep TASK-134 in backlog until the solution is accepted and integrated. This decision explicitly authorizes the **new generation namespace** as an alternative to the old destructive TASK-145 swap *only where old ownership is unproven*. It **does not** authorize dropping safety checks or fabricating past ownership.

**Provenance constraint:** Existing `reviews/TASK-147/<execution-id>.md` files are immutable. To place these normative instructions in the next worker's prompt, they must be included verbatim or accurately summarized in a **new execution-attributed curator feedback** after the next review disposition. Do not rewrite an old review or alter the TASK-147 ticket blob in the middle of the already reviewed lineage just to force prompt injection. If a genuine Architect specification revision is required, it must be guarded and scheduled as a fresh generation without misattributing old review evidence.
